## 0. 一句话定义

> **每个提示词就是一张符**：把「提示词」从一段字符串，升级为一张**有结构、有授权引用、有约束、有签名、可回放、可组合的符文**；用**箓**管理身份与工具名册，用**篆**负责编码与书写，用**法坛**执行，用**太极**编排，用**缴符**归档。UI 不是表单，而是一张可以书、敕、盖、焚、缴的符。

| 项 | 含义 |
|---|---|
| 项目名 / 仓库名 | `taoism-agent`（与本地目录名一致，**已确认**） |
| 代号 | **符箓**（FULU），仅作代号，不用于项目名与仓库名 |
| 二进制 / GUI | `fulu` /「符箓台」 |
| 核心文件后缀 | `.fu`（人可读符文 DSL）／`.fub`（紧凑二进制） |
| 文化框架 | 符（指令）· 箓（授权名册）· 篆（编码书写）· 法坛（运行时）· 太极（编排）· 缴符（审计） |

## 1. 设计公理

1. **符是一等数据对象**，不是文本框里的一段字。一张符 = 一个最小可运行的 Agent 定义，可独立保存、校验、签名、复用、回放、组合。
2. **符与箓必须分离**：符只写「要做什么 + 引用谁的授权」；密钥、身份、工具注册表、权限等级属于箓。没受箓的符不得执行。
3. **约束写在符里**（捆仙绳）：预算、超时、沙箱、工具白名单、循环上限是符的字段，不是散落的全局配置。
4. **执行是不可撤销的提交点**（焚符）：之前必须校验 + 盖印 + dry-run + 明确确认；之后必须有回执与归档。
5. **UI 与数据同构**：界面直接呈现符纸、部位、箓卷、法坛、太极、火光与回执；用户操作的对象是「符」，不是「配置项列表」。

## 3. 总体分层

```
┌───────────────────────────────────────────────────────────────┐
│  符箓台 (fulu-ui, egui/eframe 原生自绘)   │  fulu-cli (无头/CI) │  ← 表现层
├───────────────────────────────────────────────────────────────┤
│  fulu-app：用例门面 / 状态机驱动 / 事件订阅（UI 与 CLI 共用）      │  ← 应用层
├──────────────┬──────────────┬──────────────┬───────────────────┤
│ fulu-core    │ fulu-script  │ fulu-register│ fulu-audit        │  ← 领域层
│ 符文模型/DSL │ 篆：编解码   │ 箓：授权名册 │ 缴符：事件日志    │
│ 校验/符印    │ 复文/云篆    │ 凭据/权限/配额│ 回放/导出         │
├──────────────┴──────────────┴──────────────┴───────────────────┤
│  fulu-runtime（法坛：tokio 调度、Harness 约束、沙箱、事件溯源）   │  ← 运行时层
│  fulu-orchestrator（太极：多 agent 编排、DAG/消息、模型路由）      │
├──────────────┬──────────────┬──────────────────────────────────┤
│ fulu-provider│ fulu-tools   │ fulu-skills                      │  ← 适配层
│ 模型供应商   │ 风火轮工具   │ 符胆技能包（内容寻址）           │
└──────────────┴──────────────┴──────────────────────────────────┘
```

**依赖方向严格单向**：`core` 不依赖任何上层；`provider` / `tools` 以 trait 注入 `runtime`；`ui` 与 `cli` 只经 `fulu-app` 访问领域层。这样领域层可完全无头测试，GUI 框架可替换而不牵动业务。

### 3.1 符层（Talisman）

一张符的规范字段（`.fu` DSL 的形态示意，**非最终语法**）：

| 字段 | 部位 | 类型 / 约束 |
|---|---|---|
| `id`, `name`, `version`, `schema_version` | 符额 | UUID / 语义化版本，向后兼容迁移 |
| `head` | 符头 | `provider_ref` + `endpoint`（引用，不内嵌地址凭据） |
| `model` | 神明名号 | `model_id` + 采样参数 |
| `credential_ref` | 敕令 | `lu://<register>/<credential-id>`，**禁止出现任何密钥字面量** |
| `harness` | 捆仙绳 | `budget_tokens`, `timeout`, `sandbox`, `allow_tools`, `max_steps`, `network` |
| `system` / `user` | 天柱 / 地柱 | 模板字符串 + 具名变量 |
| `goal` | 所请事项 | 描述 + `success_criteria`（可判定） |
| `tool_refs` | 风火轮 | 工具 ID 列表，须在箓中已授权 |
| `skill_refs` | 符胆 | `sha256:` 内容寻址引用 |
| `output_schema` / `loop_policy` | 符脚 | 输出 schema + `max_iterations` + `until` |
| `seal` | 符印 | 规范化序列化后的 sha256 + 签名者 + 时间戳 |

设计示意（**不是代码**）：

```
fu "镇宅·长文摘要" v1
符头   -> provider_ref=lu://local/llama-server     # 内置本地模型，见 8.5
神明   -> model=lfm3-1.7b-q4km                  # 2B 级 LFM 基础模型
敕令   -> credential_ref=lu://default/local        # 只引用，不含密钥；本地模型为「无需密钥」语义
捆仙绳 -> budget_tokens=8000 timeout=60s sandbox=strict allow_tools=[fs.read] max_steps=12
天柱   -> "你是严谨的摘要助手，只依据给定文本。"
地柱   -> "{{input}}"
所请   -> goal="输出不超过 200 字摘要" success=output.len<=200
风火轮 -> tools=[fs.read]
符胆   -> skill@sha256:9f2c...
符脚   -> output=schema:summary.v1 loop=max(3) until=success
符印   -> sha256:自动由规范化内容生成
```

### 3.2 箓层（Register）

- **箓牒**：本地加密的身份与凭证库，落到系统凭据库（Windows Credential Manager / macOS Keychain / Linux Secret Service），符文件、日志、事件、导出包一律不含明文密钥。
- **神将名册 = 工具注册表**：工具 ID、能力描述、权限等级、允许路径/域名、配额，对应画面上的 `tool_1 … tool_8`。
- **授箓流程**：首次运行引导「入道 → 受箓 → 配置工具」；符执行前按「箓」核验 `credential_ref`、工具权限与配额，失败即「驳回·拒绝访问」。
- **权限等级**：只读 / 受限执行 / 完全执行，符的 `harness` 不得越权申请。

### 3.3 篆层（Script）

- **云篆**：符文矢量笔顺与版式描述，供 GUI 自绘；与语义层解耦，换字体/换皮肤不改数据。
- **复文**：常用片段字典 + 引用压缩，把重复的 system/skill 片段折叠为短符号；这是**符号化压缩**，不宣称等价于 LLM tokenizer。
- **两种序列化**：`.fu` 人可读文本（便于版本管理与评审）、`.fub` 紧凑二进制（内容寻址、导入导出）。
- **符印**：canonical 序列化（键排序、无浮点歧义、统一换行）后取 sha256，保证 Windows / macOS / Linux 得到同一哈希；校验不通过即「破符」。

### 3.4 法坛与太极（Runtime / Orchestrator）

- **法坛**：`tokio` 驱动的运行时，负责执行队列、Harness 强制（预算递减、超时中断、工具白名单、循环上限）、沙箱边界、事件溯源。
- **太极**：中心编排器把一张「主符」拆为多个子符，分派给雷/火/风/水式的专职 agent，汇总成回执；编排图是有向无环图，避免环形召唤。
- **回执/缴符**：append-only 事件日志（书符、盖印、焚符、工具调用、模型响应、结果、错误）全部脱敏后落盘，支持按符印回放与导出，用于审计与复现。

## 4. 运行机制：符箓仪轨 ↔ 状态机

| 状态 | 仪轨 | 系统动作 | 可迁移 |
|---|---|---|---|
| `Draft` 草稿 | 净坛 / 书符 | 编辑符纸，实时结构校验；缺部件即「未成符」 | 成符、破符 |
| `Formed` 成符 | 一笔呵成 | schema 校验通过、生成内容哈希、冻结内容 | 盖印、破符 |
| `Sealed` 已盖印 | 敕符 · 盖印 · 开光 | 用箓中身份签名；核验权限与配额；内容变更即失效需重新盖印 | 待焚、驳回 |
| `Pending` 待焚 | 焚符前 | dry-run：展示将调用的模型、工具、预算、影响面，等待明确确认 | 焚化、取消 |
| `Igniting` 焚化中 | 焚符上表（Enter） | 提交 provider，执行工具循环；**此点起不可撤销** | 回执、炸炉、超时 |
| `Answered` 回执 | 神回话 | 结果按 `output_schema` 校验，落回执 | 归档、重焚 |
| `Archived` 归档 | 缴符 · 复命 | 事件日志封存、只读可回放 | 只读 |

**异常态**：破符（校验/哈希不符）、驳回（未受箓或越权）、炸炉（运行时失败 / 预算耗尽）、过坛（超时）。全部写入事件日志，不做静默重试。

**一次完整时序**：书符 → 成符 → 盖印 → 待焚(dry-run) → 确认 → 焚化 → provider 调用 → 工具调用 → 反馈 → 符脚判定收敛（未达标则回到循环，受 `max_iterations` 硬限）→ 回执 → 缴符归档。

## 5. Workspace 模块划分

| Crate | 职责 | 关键约束 |
|---|---|---|
| `fulu-core` | 符文模型、DSL 解析、结构校验、符印哈希、状态机定义 | 纯函数优先，零 I/O，快照测试 |
| `fulu-script` | `.fu` / `.fub` 编解码、复文字典、云篆矢量描述、canonical 序列化 | 跨平台哈希一致性测试 |
| `fulu-register` | 箓牒、系统凭据库、工具注册表、权限与配额 | 密钥零落盘明文，日志脱敏 |
| `fulu-runtime` | 法坛：调度、Harness 强制、沙箱、事件产生 | 与 provider/tools 通过 trait 解耦 |
| `fulu-orchestrator` | 太极：多 agent 编排、DAG、模型路由、汇总 | 禁止环形分派 |
| `fulu-provider` | 模型供应商适配（云端 HTTP/SSE、本地模型） | 超时/重试/流式统一抽象 |
| `fulu-model` | **新增**：内置模型清单、SHA256 校验、下载/导入、本地推理进程生命周期 | 权重不进 Git；清单是唯一事实源 |
| `fulu-tools` | 风火轮：工具 trait、白名单、最小权限执行 | 路径/域名边界，子进程隔离 |
| `fulu-skills` | 符胆：技能包版本化、内容寻址、全局发现、导入导出 | sha256 校验 |
| `fulu-mcp` | **v0.3 新增**：全局 MCP 配置发现（只读）、stdio JSON-RPC 客户端、MCP 工具 → 统一 `ToolCall` 适配 | 只展示不管理；子进程隔离、超时与输出上限；server 输出视为不可信文本 |
| `fulu-context` | **v0.3 新增**：会话上下文采集（无授权硬件信息、IP 所在地、OS/运行时指纹） | 全项容错、可关闭；只进会话头与缴符事件，不进符文正文 |
| `fulu-prompt` | **v0.3 新增**：分层系统提示词装配器（固定小节 + full/minimal 档位） | 纯函数装配，快照测试锁定；逐层截断上限 + 总上限 |
| `fulu-audit` | 缴符：append-only 事件日志、回放、导出 | 脱敏、可校验链 |
| `fulu-app` | 用例门面：状态机驱动、事件订阅 | UI 与 CLI 共用同一门面 |
| `fulu-ui` | 符箓台 GUI（egui/eframe 原生自绘） | 不含业务逻辑，可整体替换 |
| `fulu-cli` | 无头运行、批量校验、CI 集成 | 与 GUI 行为一致 |

共享错误/事件类型置于 `fulu-core`，避免跨 crate 循环依赖。

## 6. GUI 框架选型评估（非 Web · 跨平台 · 低资源）

### 6.1 硬门槛

| 门槛 | 淘汰对象 |
|---|---|
| **非 Web / 无 WebView** | Tauri、Dioxus Desktop（系统 WebView，违背「非 web」且内存与进程开销更高） |
| **许可与 MIT 兼容** | Slint（GPLv3 / 商业双许可，链接后与本仓库 MIT 冲突；且 `.slint` DSL 把 UI 拆出 Rust 类型系统） |
| **无重型系统运行时依赖** | relm4 / GTK4（Windows、macOS 需随包分发 GTK 运行时，违背低资源与单文件分发） |

### 6.2 加权评分（1–5 分，按权重折算为百分制）

| 维度（权重） | egui/eframe 0.37 | iced 0.14 | GPUI | FLTK-rs |
|---|---|---|---|---|
| 跨平台桌面覆盖 (20) | 5 → 20 | 4 → 16 | 3 → 12 | 4 → 16 |
| 低资源：体积/内存/启动 (20) | 5 → 20 | 4 → 16 | 4 → 16 | 5 → 20 |
| 自绘符文：路径/画布/动效 (20) | 5 → 20 | 4 → 16 | 5 → 20 | 2 → 8 |
| 中文 CJK 字体与输入法 (15) | 3 → 9 | 3 → 9 | 4 → 12 | 3 → 9 |
| 架构可维护 / 可测试 (15) | 3 → 9 | 5 → 15 | 3 → 9 | 2 → 6 |
| 生态成熟度 / 文档 (10) | 5 → 10 | 4 → 8 | 2 → 4 | 3 → 6 |
| **总分** | **88** | **80** | **73** | **65** |

补充判断：egui 的即时模式对「符纸按帧自绘、部位热区、笔顺动画、火光粒子」极其契合，最小二进制约 5 MB 级；代价是复杂状态管理要自建——这由 `fulu-app` 状态机承担，恰好把职责分开。iced 的 Elm 架构在可维护性上更强，作为**备选**；GPUI 绑定编辑器生态演进、平台覆盖与稳定性不足；FLTK 自绘能力不足以承载符文。

### 6.3 结论与本机实测

**主选：`egui 0.37 + eframe 0.37`，关闭默认 features，启用 `glow` + `default_fonts`**（避免默认 `wgpu` 带来的体积与显卡驱动依赖），符文用 epaint 自绘矢量路径，不引入任何 WebView。CJK 采用思源宋体 / Noto Serif CJK 子集（SIL OFL，与 MIT 兼容），随包内置以保证三平台一致。

本机工具链实测（2026-11-10）：

| 项 | 结果 |
|---|---|
| `rustc` / `cargo` | 1.99.1 / 1.99.1，默认 target `x86_64-pc-windows-msvc` |
| 最小 Rust 程序编译运行 | 通过 |
| 依赖源 | 已配置 `rsproxy-sparse` 国内镜像，索引与 crate 下载正常 |
| `egui` / `eframe` | 0.37.0，MIT OR Apache-2.0，MSRV 1.95（本机 1.99.1 满足） |
| `iced` | 0.14.0，MIT，MSRV 1.88（备选可编译） |
| 裁剪版 `eframe(glow)` 依赖链编译验证 | 见文末「验证记录」 |

## 8. GitHub 托管与跨平台发布设计

### 8.1 仓库与工作流

- 现状：`main` ↔ `origin/main`，SSH 远端，MIT，初始提交仅 `.gitignore` / `LICENSE` / `README.md`。
- 策略：`main` 保护 + 短分支 PR；`v*` tag 触发发布；所有密钥走 GitHub Secrets，仓库内零明文。
- 两条工作流（**评审通过后落地为 `.github/workflows/*.yml`，本轮不创建**）：
  - `ci.yml`：`cargo fmt --check`、`cargo clippy -D warnings`、`cargo test --workspace`、`cargo deny check`（许可证 + 公告）、`cargo audit`；每个平台矩阵至少跑一次编译。
  - `release.yml`：tag 触发 → 矩阵构建 → 打包 → 校验和 → SBOM → 上传 Release。

### 8.2 构建矩阵与产物

| Runner | Target | 产物 |
|---|---|---|
| `windows-latest` | `x86_64-pc-windows-msvc` | `.msi`（WiX）、`.zip` |
| `macos-15-intel` | `x86_64-apple-darwin` | `.dmg`、`.tar.gz` |
| `macos-15` | `aarch64-apple-darwin` | `.dmg`、`.tar.gz` |
| `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | `.AppImage`、`.deb`、`.tar.gz` |

> 2026-11-11 注：GitHub 已于 2026-11-02 退役 macOS 13/14 镜像，runner 标签从 `macos-13`/`macos-14` 迁移到 `macos-15-intel`/`macos-15`（提交 da22594）。
| 第二阶段（可选） | `aarch64-unknown-linux-gnu` | ARM64 Linux 原生 runner 或 `cross`，视可用性决定 |

`release.yml` 核心设计（**草案，非仓库文件**）：

### 8.3 低资源编译配置

Release profile：`lto = "thin"`（或 `true`）、`codegen-units = 1`、`strip = true`、`panic = "abort"`、`opt-level = "z"` 或 `3` 按基准取舍；eframe 关闭默认 features 只保留 `glow`；字体做 CJK 子集而非整包；不打包 WebView 运行时。这些是**设计目标**，M1 起用实测数据校准。

### 8.4 开源合规

依赖统一 MIT / Apache-2.0 / OFL 白名单；`cargo deny` 在 CI 中阻断 GPL/LGPL 传染性依赖；符文样例、图标、字体均自建或取兼容许可素材；视频分析文档属对他人作品的评论性引用，不含原片与第三方源码。**模型权重单独按 8.5 的许可隔离规则管理，不受仓库 MIT 覆盖。**

### 8.5 内置本地基础模型（2026-11-10 决策，M0 落地）

**决策**：项目自带一个 2B 级 LFM 本地基础模型，作为「符头 → 神明名号」的默认落点。默认路径完全离线、不需要任何 API Key；云端供应商保留为可选 provider，不进默认路径。

#### 型号矩阵（`models/manifest.json` 为唯一事实源）

| 槽位 | 型号 | 参数量 | 量化文件 | 体积 | 上下文 | 运行时要求 | 定位 |
|---|---|---|---|---|---|---|---|
| `default` | `LiquidAI/LFM3-1.7B-GGUF` | 1.73B（官方归类 2B 级） | `LFM3-1.7B-Q4_K_M.gguf` | 1.1 GB | 256K | llama.cpp ≥ b11960 / v0.8.0 | **默认**：2026-10-27 发布，三混合架构，专为本地 agent 与工具调用后训练 |
| `fallback` | `LiquidAI/LFM2-2.6B-GGUF` | 2,569,272,320 | `LFM2-2.6B-Q4_K_M.gguf` | 1.56 GB | 32K | llama.cpp 支持 `lfm2`；candle 有 `quantized-lfm2` 官方示例 | **备选**：生态最成熟、纯 Rust 后端可直接验证 |
| 低内存档 | `LiquidAI/LFM3-1.7B-GGUF` | 1.73B | `LFM3-1.7B-QAD-Q4_0.gguf`（量化感知蒸馏） | 1.05 GB | 256K | 同上 | 可选，适合 ≤4 GB 内存设备 |
| **不作运行模型** | `LiquidAI/LFM3-1.7B-Base` | 1.73B | 仅 BF16 safetensors | 3.46 GB | 256K | 无 GGUF、无指令跟随 | 纯预训练底座，只用于自行微调，**不能内置直接推理** |

> 术语澄清：用户所说「2B 的 LFM 基础模型」按**可运行的 2B 级本地底座**理解，落到 `LFM3-1.7B` 的 GGUF；若指的是 `LFM3-1.7B-Base` 这个微调底本，只需把它登记为 `finetune_base` 槽位、运行时仍指向 `default`。切换型号 = 改 manifest 一行，代码零改动。
>
> 两代模型均支持中文。推荐采样：LFM3 通用 `temperature=0.1, top_k=50, repeat_penalty=1.1`；LFM2 `temperature=0.3, min_p=0.15, repeat_penalty=1.05`。LFM2 家族的 ChatML 模板与 Pythonic 工具调用格式由 `fulu-provider` 归一为统一 `ToolCall`，模型差异不外泄到符文与 Harness。

#### 关键架构判断：内置模型 ≠ 内嵌推理引擎

Rust 侧**不链接 C++ 推理库、不把 GGUF 解析进主进程**；改为随包／按平台提供 `llama-server`（OpenAI 兼容 HTTP，仅绑定 `127.0.0.1` 随机端口），`fulu-provider::LocalLfmProvider` 只通过 HTTP 与它对话。理由：

1. **与架构迭代解耦**：换 lfm2 → lfm3 乃至后续版本，只需换运行时版本，不必重编 Rust 或等待 Rust 绑定跟进新架构；
2. **CI 不爆炸**：避免三平台 C++ 工具链与 CUDA/Metal/Vulkan feature 矩阵；
3. **故障隔离**：推理进程崩溃／OOM 不拖垮 GUI，法坛可捕获为「炸炉」；
4. **许可边界清晰**：llama.cpp（MIT）与权重（lfm1.0）各自独立分发；
5. **低资源**：空闲不启动推理进程，按需拉起、闲置超时自动退出。

M3 再评估内嵌后端：`llama-cpp-2`（GGUF 全架构、需 C++ 构建）与 `candle::quantized_lfm2`（纯 Rust、仅 LFM2）。二者当前**不进默认依赖**。

#### 分发两档

- **A 轻量包（默认）**：不含权重。首次运行 `fulu model fetch` 按 manifest 下载到用户数据目录，断点续传 + SHA256 校验 + 原子落盘；离线环境用 `fulu model import <file>` 从本地导入。缺权重时 CLI/GUI 给出明确指引，不静默联网。
- **B 离线 bundle（Release 可选资产）**：含权重 + `THIRD_PARTY_NOTICES.md` + LFM LICENSE 原文，供完全离线部署；由 `workflow_dispatch` 手动触发，不在每次 tag 自动上传 1.1 GB。
- 权重**不进 Git**（单文件体积与 LFS 成本都不合适），仓库只留清单、校验逻辑与合规文本。

#### 许可隔离（阻断性合规项）

- 仓库代码是 **MIT**；模型权重是 **LFM Open License v1.0**（基于 Apache 2.0，新增 Section 5 商用营收门槛）。二者是不同客体、不同许可，**不得把权重声明为 MIT**，也不得因打包而弱化下游的 lfm1.0 义务。
- lfm1.0 要点：年营收 **< 1000 万美元**的实体可免费商用；**≥ 1000 万美元**（按 Legal Entity 合并计算母／子／关联公司）需向 Liquid AI 另购商业许可；研究、内部评测与合格非营利组织不受该门槛；无 copyleft 要求；分发时必须附 LICENSE 全文、保留版权／归属／NOTICE、标注被修改文件，且不得用 Liquid AI 商标做背书。
- 因此：随包附 `THIRD_PARTY_NOTICES.md` 与 LICENSE 原文；`models/README.md` 写明下游义务；CI 增加 manifest 许可字段断言；**产品化前必须做法务复核**，年营收达标或不能接受该条款时，改用自带许可的模型或取得商业授权。这不是技术验证能豁免的。
- `cargo deny` 只管 Rust 依赖；模型权重由上述清单与通知文件独立管控。

#### 与符箓体系的映射

| 部位 | 本地模型下的取值 |
|---|---|
| 符头 | `provider_ref=lu://local/llama-server` |
| 神明名号 | `model_id=lfm3-1.7b-q4km`（可切 `lfm2-2.6b-q4km`） |
| 敕令 | `credential_ref=lu://default/local`，语义为「无需密钥」；字段保留，符内仍禁止任何密钥字面量 |
| 风火轮 | LFM3 原生工具调用归一为统一 `ToolCall`，由「箓」做白名单核验后才执行 |
| 符胆／缴符 | 本地推理同样写事件日志，默认只记 token 数与耗时，不记完整 prompt 明文 |

#### 预算修正

9.3 的「空闲内存 ≤ 80 MB／发布包 ≤ 20 MB」指**不含模型权重与推理进程**的默认轻量包；Q4_K_M 权重约 1.1 GB，默认 `n_ctx=8192`（不全开 256K）以控制 KV cache，推理进程按需拉起、闲置退出。离线 bundle 体积单独计。
**（2026-11-11 实测修订）** 80 MB 是无 GUI 口径：CLI 实测峰值 8.39 MB，而 GUI 空闲 97.6 MB 工作集，故 9.3 已拆为 CLI ≤ 12 MB / GUI ≤ 130 MB 两档，详见第 35 节。

### 8.6 全局 MCP 与技能包：只展示，不管理（2026-11-10 决策）

**原则：符箓是消费者，不是管理者。** 全局 MCP 服务与技能包的安装、升级、删除一律由用户在原有生态里完成；fulu 只做**发现、校验、展示与接入**，绝不写任何全局配置文件。

#### MCP 接入（新 crate `fulu-mcp`）

- **发现（只读）**：按平台扫描全局 MCP 配置（`~/.workbuddy/mcp.json` 及同构格式的其他已知路径），解析出 server 名称、启动命令、env 声明（**只显示「是否有 env / 是否含疑似密钥字段」，永不显示值**）、传输方式；发现结果在符箓台「箓牒 · 外宗」页与 `fulu mcp list` 只读展示，不可在 fulu 内增删改。
- **传输**：M0 约束的延伸——只实现 **stdio 传输**（spawn 子进程，JSON-RPC 2.0 按行分隔），`initialize → tools/list → tools/call` 握手；Streamable HTTP / SSE 传输列为后续评估，不阻塞主链路。
- **工具化**：每次焚符前对启用的 server 执行一次 `tools/list` 缓存，把 MCP 工具适配为统一 `ToolCall`，走与内置工具完全相同的「箓」白名单 / 配额 / 边界核验——**不因来源是第三方就绕过风火轮三道闸门**。
- **权限默认值**：外宗箓默认「受限」级 + **每次调用单独确认**；用户可在箓中把单个 server 升级为自动放行（写入的是 fulu 自己的会话配置，不是全局 MCP 配置）。
- **故障语义**：server 崩溃 / 超时 / 输出超限 = 「外宗失联」事件，写入缴符并降级继续；server 输出一律视为**不可信文本**，绝不并入系统提示词第 0 层（篆心），只能作为工具结果进入当轮对话。
- **隔离**：子进程独立、8 MiB 输出上限、按调用超时硬限，异常不拖垮法坛主进程。

#### 技能包（扩展 `fulu-skills`）

- 扫描全局技能目录（已知路径 + 可配置），读取每个技能包的元数据（名称、版本、入口文件、sha256 内容摘要）并展示；发现即展示，**不复制、不修改、不安装**。
- 成符时技能包作为「符胆」候选被**引用**：符文记录 `skill 名@内容摘要`，运行时按摘要重新校验——全局技能在两次焚符之间被改动，符印校验即失败并提示重新成符（与「dry-run 后符文变更即破符」同一语义）。

### 8.7 内置五件套：agent 基本能力的风火轮

| 工具 | 符箓名 | 职责 | 实现要点 | 里程碑 |
|---|---|---|---|---|
| 内置浏览器 | **moli** | 网页抓取与轻交互 | 无头 HTTP(S) 抓取 + HTML→文本抽取；**不嵌 WebView**（6.1 硬门槛不破），JS 渲染页暂不支持并如实提示；**首个 TLS 依赖例外**（8.4 白名单单列） | M3 |

| 子智能体 | **召将** | 并行 / 委托 | 每个将 = 一张子符：`promptMode=minimal` 提示词档（见 8.9）、独立缴符段、独立 token 预算；由太极分派，**禁止环回分派**（将不得再召将，M3 先单向一层） | M3 |

五件套全部实现 `fulu-tools` 的工具 trait，统一过箓、统一进缴符；**没有任何工具绕过盖印 / 确认闸门的通道**。

### 8.8 会话上下文采集（会话头）

每次新会话启动采集一次，装配进系统提示词第 1 层（见 8.9），并写一条缴符会话事件；**只进会话头与缴符事件，绝不写进符文正文**（符的可移植性不受本机指纹污染）。

- **采集范围（全部无需系统授权）**：OS 名称/版本/架构、内核版本、CPU 型号与核数、内存总量、工作区所在卷的可用磁盘、显示器分辨率、locale/时区、fulu 版本。实现走标准库 + 平台命令（`/proc`、`Get-CimInstance`、`sysctl` 等），**不引入采集类第三方 crate**。
- **IP 所在地**：best-effort HTTPS 查询（复用 8.4 TLS 例外），**只取国家/城市/ISP 粗粒度**；失败静默降级为「未知」，不重试轰炸；`context.ip_location = on/off` 可关，默认 on，会话头明示「采集来源与时间」。
- **容错**：任何一项失败都降级为「未知」并继续，采集不阻塞会话启动。
- **明确不做**：不读摄像头/麦克风/精确地理位置等需授权项；不采集硬件序列号、MAC 地址等可跟踪标识。

### 8.9 系统提示词分层（参考 OpenClaw 的分开规划）

参考 OpenClaw 的「系统提示词按固定小节装配 + 工作区文件注入 + 权限阶梯」思想（**只借鉴组织方式，不复制任何实现**）：提示词由独立来源的小节装配，一次装配、快照测试锁定顺序，权限分层明确。

| 层 | 内容 | 来源与写入权限 | 刷新时机 |
|---|---|---|---|
| 0 篆心 | 核心身份与铁律（符箓体系规则、安全约束） | 只读，随二进制 embed | 随版本 |
| 1 会话头 | 时间/时区、硬件、IP 所在地、运行时 | `fulu-context` 采集 | 每会话一次 |
| 2 环境外宗 | MCP servers 与技能包发现摘要、工具 schema | 只读发现结果 | 每会话刷新 |
| 3 用户画像 | 习惯、偏好 | `fulu/user.md`，**用户锁定写入权** | 用户编辑 |
| 4 灵魂 | AI 性格与风格 | `fulu/soul.md`，AI 可在缴符中**提案**修改，需用户盖印生效 | 盖印生效 |
| 5 工作区约定 | 项目铁律 | workspace 内 `fulu.agents.md`，**人类锁定** | 项目定义 |
| 6 符文正文 | 当前焚化的那张符 | 不属装配器，由 Harness 注入 | 每次焚符 |

- **三档 promptMode**（对应 OpenClaw full/minimal/none 的分档思想）：`full` 主会话全量；`minimal` 召将子符（只含 0/1 精简 + 符文）；`none` 纯机械调用。
- **预算防线**：每层独立截断上限 + 装配总上限（防止上下文爆仓，超限截断并标注 `TRUNCATED`）；`fulu context show` 提供逐层占用自检。
- **默认模型约束**：2B 级模型的全档提示词控制在 ~4K tokens 内，短句、少嵌套列表、中文为主。
- 装配器是**纯函数**（`fulu-prompt`）：输入各层文本快照，输出最终提示词；可无头测试、可快照锁定。

### 8.10 引符：默认模型的开箱基础配置（first-run）

**目标：装好即用**——不下载云端密钥、不强制联网，默认模型（lfm3-1.7b-q4km）就能完成基础会话与基础配置。

- **首次启动流程**：`fulu-context` 采集会话头 → 提示词分层装配 → 内置「引符」（预置符文）驱动默认模型做对话式引导：确认语言与工作区目录 → 展示 MCP／技能包发现结果 → 解释盖印 / dry-run / 确认闸门 → 生成第一张示例符。`fulu doctor` 提供同一信息的无模型版本作为兜底。
- **能力边界如实标注**：2B 级默认模型承担「会话式基础配置 + 简单问答 + 单工具调用」；不承诺复杂多步推理，复杂任务引导用户挂载更强模型（改符头神明名号或接云端 provider）。
- **引符也走完整仪轨**：引符是预置符文，同样经过成符→盖印→dry-run→确认；从第一天起 GUI/CLI/缴符路径一致，不存在绕过仪轨的「系统直连」。
- 真机验证依赖权重导入；协议层验证与 M2 相同，用 mock OpenAI 兼容服务覆盖（不伪装为模型效果验证）。

## 13. M2 实施补记（2026-11-10 下午，本机 `x86_64-pc-windows-msvc`）

### 13.1 实现取舍：同步执行器，零新增第三方依赖

架构 3.4 写法坛为「tokio 驱动的运行时」。M2 实现时**有意推迟 tokio**，改为同步执行器 + 可注入 `Provider` / `ToolRegistry`：

- 单符循环是「一次 HTTP → 可选工具 → 再 HTTP」的严格串行过程，引入整个异步运行时不带来吞吐收益，却会显著增加依赖面、编译时间与常驻内存（与 9.3 低资源预算冲突）；
- `Provider` 是 trait，M3 换异步实现只需替换适配层，`fulu-runtime` 的状态机与仪轨不变；
- 超时由 `Instant` + `TcpStream` 读写超时双重控制，预算与步数在每步入口强制，异常态立即写事件并返回，**不静默重试**。

因此本轮**没有新增任何第三方 crate**：`fulu-provider::http` 用 `std::net::TcpStream` 实现了一个约 200 行的最小 HTTP/1.1 客户端，只接受 `127.0.0.1` / `localhost`，支持 `Content-Length` 与 chunked、8 MiB 响应上限、非 2xx 不吞错。**它不支持 HTTPS，也不负责公网下载**——这是刻意的能力边界，不是遗漏。

### 13.2 逐层落地

| 层 | 本轮实现 |
|---|---|
| 符 / 篆 | M0 已有；新增 dry-run 后符印复核：符文在待焚期被改动即「破符」，必须重新成符盖印 |
| 箓 `fulu-register` | 权限等级（只读/受限/完全）、工具名册、路径/域名边界、调用配额、凭据「是否受箓」；越权在盖印前驳回 |
| 风火轮 `fulu-tools` | `echo` / `fs.read` 两个只读工具；白名单 + 配额 + 工具自身路径校验三道；拒绝绝对路径与 `..` 穿越，单次读取上限 64 KiB |
| 法坛 `fulu-runtime` | `prepare`（成符→盖印→待焚，**零网络**）与 `ignite`（确认→焚化→请神/召将循环→符脚判定→回执→归档）；Harness 预算/超时/步数硬限 |
| 符脚 `converge` | `success_criteria` 落到可判定谓词：`success` / `nonempty` / `output.len` 五种比较 / `contains:<文本>`；**不认识的判据在待焚前直接破符**，绝不焚化后假装完成；长度按 Unicode 字符数 |
| 缴符 `fulu-audit` | append-only JSONL + `sha256(prev_digest ‖ canonical(event))` 可校验链、按符印回放、导出；写入前统一脱敏，日志不落 prompt 明文与密钥 |
| provider | OpenAI 兼容 `/health`、`/v1/models`、`/v1/chat/completions`；LFM3 原生 `tool_calls`、旧式 `function_call`、LFM2 Pythonic `name(k=v)` 三种载体归一为统一 `ToolCall`；服务端未给 usage 时按字符数估算并**明确标注 `estimated`** |

## 14. v0.3 能力面增量设计记录（2026-11-10 傍晚）

### 14.1 需求来源与结论

用户于 M2 完成后提出五项能力面需求，全部并入架构（8.6–8.10），**本轮只落设计与 crate 占位骨架，不含业务实现**：

4. **系统提示词分层**：参考 OpenClaw 的固定小节装配与权限阶梯思想（只借鉴组织方式，不复制实现），七层来源 + full/minimal/none 三档（8.9）。
5. **默认模型开箱**：内置「引符」让 2B 级默认模型完成对话式基础配置与基础运行，引符同样走完整仪轨（8.10）。

### 14.2 结构影响

- workspace 从 13 crate 扩到 **16 crate**：新增 `fulu-mcp`、`fulu-context`、`fulu-prompt`（本轮均为占位骨架，M2.5 落地）。
- 依赖白名单唯一例外：TLS（rustls 系），供 moli／问天／IP 所在地查询使用；provider「仅回环、无 HTTPS」边界**不变**，回环链路仍走标准库最小 HTTP 客户端。
- OpenClaw 关系声明：仅参考其「提示词分节装配、权限阶梯（人类锁定 > AI 可改 > 完全开放）、分档 promptMode」的公开设计思想，未接触、未复制其任何源码，与仓库原创声明一致。

### 14.3 合理性评估（增量部分）

- **与既有安全模型同构**：MCP server=「外宗箓」、技能包=符胆引用（摘要校验失败即破符）、五件套=风火轮工具，都不需要新的信任模型；
- **边界清晰**：采集范围白名单化、MCP 输出视为不可信文本、摄行最高权限默认禁用，隐私与安全风险各有缓解行（9.2 已更新）；

- **遗留风险**：2B 模型驱动引符对话的实际质量未知（协议链路可 mock 验证，模型效果必须真机评估）；MCP stdio 子进程在 Windows 的 spawn 环境继承需实测。

**结论：增量设计合理，并入 v0.3；实施顺序 M2.1 → M2.5 → M3（待用户确认）。**

## 16. M3 实施补记：外宗接进法坛 + 符箓台（2026-11-10 夜，本机 `x86_64-pc-windows-msvc`）

### 16.1 本轮解决的两个真缺口

M2.5 收尾时留了两条「说得比做得多」的地方，本轮把它们做实：

1. **外宗（MCP）工具进不了仪轨循环**。M2.5 只有「能连上、能列工具」，`AltarSession` 里根本没有外宗工具，`build_tools_json` 也把所有未知工具的参数写成空对象——模型即使想调也调不动。本轮把「发现 → 握手 → 箓登记 → 下发 schema → 焚符时调用 → 回执入链」整条路径打通，并用真实 HTTP + 真实子进程做了集成测试。
2. **符箓台还是 M0 的 IME 探针**。本轮换成三栏法坛界面（符箓 / 法坛 / 缴符），把「成符→盖印→待焚→确认→焚化」做成看得见的按钮序列，焚符走后台线程不卡界面。

### 16.2 逐模块落地

## 17. M3.1 实施补记：外宗逐工具分级与敕门（2026-11-10 深夜，本机 `x86_64-pc-windows-msvc`）

### 17.1 上一轮留下的粗粒度

第 16 节把外宗工具接进了仪轨循环，但权限只能给到「受限级」这一个档：接一台带 `stop_process` 的 server，等于把「停进程」这个能力整体放进了自动循环。当时的处理是「靠可见性管理」——符点名 + dry-run 展示 + 缴符留痕。这对**只读**的 MCP 工具是过度惩罚，对**破坏性**工具又不够。

本轮补的是第二维：**同不同意这一次调用**。它与权限正交——

- `Permission` 回答「这张符最多能碰到什么」（箓层，静态）；
- `RiskClass` 回答「碰到之前要不要人点头」（敕门，逐次）。

### 17.2 设计

**三档风险，对应三种确认强度**（`fulu-register::RiskClass`）：

| 等级 | 含义 | 确认方式 |
|---|---|---|
| `Observe` | 只读观察，无副作用 | 免确认 |
| `Mutate` | 可变更、可回滚（起进程、写文件、调接口） | 每张符确认一次 |
| `Destructive` | 破坏性且不可逆 | 每次调用都要确认 |

**风险等级与权限等级一样随授权下发**（`Authorization.risks`），不是让执行层回头查名册——「忘记查名册就静默执行高危工具」这种漏法不能留。查不到等级的工具按 `Destructive` 处理，不给「漏登记 = 免确认」留口子。`ToolGrant` 的 `risk` 字段在反序列化时缺省也是 `Destructive`。

**敕门是一个 trait，不是布尔开关**（`fulu-runtime::gate`）：

```rust
pub trait Confirmer: Send {
    fn confirm(&mut self, request: &ConfirmRequest) -> ConfirmVerdict;
}
```

之所以是 trait：CLI 要在终端里问人，GUI 要把请求丢回界面线程，批处理要按上限放行——三种「人」不一样，法坛不该替它们选。`Altar` **不装确认器时一律敕否**（fail closed），并且这个「没装」在缴符里看得见（`EventKind::Denied` + 原因「无人值守」）。

**被拒不是炸炉**。拒绝的召将会把理由交回模型（`[召将未获确认 X] …风险等级 … 请改用不需要确认的路径`），让它换一条路；同一工具连续被拒超过 `MAX_DENIALS_PER_TOOL = 2` 次才停止焚化——模型很擅长换个说法再试，而每次拒绝都在烧 token 预算。

**外宗的风险来自 server 自述，只用于收紧**。MCP 的 `annotations` 解析成 `RiskClass` 的规则：

| annotations | 判定 |
|---|---|
| `destructiveHint: true` | `Destructive`（显式说了破坏性，别的字段一概不看） |
| `readOnlyHint: true` 且未说破坏性 | `Observe`（免确认；**权限仍是 `Limited`**） |
| `destructiveHint: false` | `Mutate` |
| 什么都没说 | `Destructive`（规范缺省） |

自述只影响「要不要问人」，从不放宽权限——外宗工具永远停在 `Limited`，符必须 `sandbox: limited` 且逐个点名。

### 17.3 真机发现：自述缺失是常态

本机 `cucumber` server 的 **9 个工具一个 `annotations` 都没写**，于是全部落到 `Destructive`——包括 `get_dashboard`、`list_processes`、`query_logs` 这些明显只读的。按「不采信沉默」处理是对的，但结果是 9/9 都需要人确认，实际用起来等于每张符都要 `--allow-risk destructive`，比原来的粗粒度更糟。

因此补了一张 **fulu 自己的**风险覆盖表 `~/.fulu/outer-sect-risk.json`（`fulu-mcp::RiskOverrides`）：

```json
{ "tools": {
  "mcp.cucumber.get_dashboard": "observe",
  "mcp.cucumber.start_process": "mutate"
} }
```

边界刻意划清：

- 这是 **fulu 的配置**，不是 MCP 生态的配置——不改 server 的声明，也不碰它的安装/升级/删除；
- 只能按工具全名逐条声明，**不做模糊匹配**：猜错的代价是放行一个破坏性操作；
- 坏条目逐条报 issue 而不猜测（`"harmless"`、`3` 都会被拒并说明原因）；
- 指向已不存在工具的条目会单独点出来（多半是 server 升级改名），避免用户以为覆盖生效了；
- 等级来源全程可追溯：`RiskSource::{Declared, Override, Undeclared, Floor}`，界面上写「谁说的」。

策略下限（`--strict-outer-sect`）只向上抬，覆盖表在它之下不可见——两者都只影响确认，不影响权限。

## 18. M3.2 实施补记：GUI 逐次弹窗敕门 + 内嵌中文字体（2026-11-11 凌晨，本机 `x86_64-pc-windows-msvc`）

### 18.1 逐次弹窗敕门（第 17.6 节遗留项 2 的兑现）

把「GUI 一次性预授权」升级为**默认逐次问人**，线程模型：

1. 焚符线程拿到 `AltarSession` 前，门面装入 `ChannelConfirmer`（实现 `Confirmer`，随会话整体 `Box` 进线程——`AltarSession.confirmer` 是 `Option<Box<dyn Confirmer>>`，所有权转移，无自借用）。
2. `ChannelConfirmer::confirm()`：把 `ConfirmRequest` 连同**本次专用的回执通道**发进界面收件箱 → `ctx.request_repaint()` 立刻叫醒界面 → **阻塞**等回执。焚符循环本就串行，阻塞等的就是「人点头」。
3. 界面线程每帧从收件箱 `try_recv`（`Arc<Mutex<Receiver>>`），法坛面板渲染「敕门」卡片：工具名、风险等级、确认档位、第几次、描述、**参数原文**（模型输出原样展示不解释），「敕可 / 敕否」两个按钮，答完即弃。
4. **fail closed 三连**：窗口已关（发送失败）、回执通道断开、收件箱锁异常 → 一律敕否，绝不放行。
5. 旧的一次性预授权保留为显式勾选「免逐次弹窗：预授权放行全部高危召将」（默认不勾），两种路径都记入缴符。

| 位置 | 本轮实现 |
|---|---|
| `fulu-app` | 重导出 `Confirmation`（GUI 构造敕门卡片需要） |
| `fulu-ui` | 新模块 `confirm.rs`：`ConfirmExchange` 类型、`ChannelConfirmer`；`FuluApp` 增 `ctx` / `confirm_inbox` / `pending_confirm`；`logic()` 轮询收件箱；法坛渲染敕门卡片 |

### 18.2 内嵌中文字体（GUI 中文此前实为方块）

egui 自带 `epaint_default_fonts` 只有 **Ubuntu 字体**（拉丁主流选择）与 NotoEmoji，**零 CJK 字形**且不回退系统字体——第 16 节「中文渲染正常」的说法是错的，实际全是豆腐块，M0 的 IME 探针也无法人工验收。

字体策略定为**内嵌**（用户拍板：字体我们自己配，用最流行的）：

- 拉丁字母：Ubuntu 字体（egui 自带，不额外处理）。
- 汉字：**思源黑体简中子集**（Noto Sans CJK SC，SIL OFL 1.1，可再分发的最流行中文字体）：`fontTools.subset` 截取 U+4E00–9FFF 全部 20902 汉字 + 常用标点符号，16.4 MB → 6.3 MB，`include_bytes!` 编进二进制，**不依赖用户机器装了什么**。
- 生僻字兜底：子集刻意不含扩展 A 区，缺字时按平台固定候选路径回退系统 CJK 字体（只读、不分发）。
- 许可义务：OFL 全文随 `crates/fulu-ui/assets/fonts/LICENSE-NotoSansSC.txt` 入库；M4 打包清单必须随包携带（见 `THIRD_PARTY_NOTICES.md` 第 4 节）。
- 测试锁定契约：内嵌 OTF 头与体积、关键汉字在 egui 装配后的字体表中逐字可解析（无窗口 `run_ui` 一帧后经 `ctx.fonts_mut` 验证）。

| 确定性 | 拓扑序按「层」推进、层内按节点 id 字典序，同一张图永远得到同一张回执 |
| 失败不蔓延 | 依赖失败/被跳过的节点标 `Skipped`，独立分支照常执行；预算耗尽后剩余节点也标 `Skipped` |
| 执行前拒绝 | 空图 / 环 / 未知依赖 / 重名 / 重复依赖 / 自环 / 超节点数(32) / 超深度(16) / 缺符文 / 坏 JSON 全部在图校验阶段报错 |
| 不伪装成功 | `OrchestrationReceipt.converged` 只在**全部节点成功且各自收敛**时为 true；任一失败或跳过都是 false |

### 20.2 接入形态

- `TaijiGraph` / `GraphNode`（`fu_text` 原文或 `fu_path` 相对路径）/ `OrchestrationReceipt` / `NodeResult` / `NodeStatus` 经 `fulu-app` 重导出，UI 不直连编排器。
- `fulu_app::load_taiji_graph()` 只读符图与符文文件，`fu_path` 相对符图所在目录解析。
- `AltarSession::run_taiji(graph, confirmed)`：每个节点走**完整仪轨**（成符 → 盖印 → dry-run → 显式确认 → 焚化），共用一个会话与一本缴符；`confirmed` 由用户显式给出，编排器绝不替人点头。
- CLI `fulu taiji run <符图.json> --confirm`：打印拓扑序、逐节点结果、汇总，支持 `--endpoint` / `--workspace` / `--export` / `--prompt-mode` / `--no-context` / `--context-ip`。

### 20.3 顺带修复

## 22. T11 多符并发 / tokio 调度评估（2026-11-11，TODO.md S2）

**结论：明确保持同步（有意不做），不引入 tokio。** 这是一条设计结论而不是遗留欠账，文档口径从「留到 M3」改为「有意不做」。

### 22.1 论证

| 维度 | 事实 | 推论 |
|---|---|---|
| 吞吐瓶颈 | 推理走本机 `llama-server`（单实例，CPU/单卡），单次请神的耗时以秒计；法坛的 HTTP/JSON/缴符开销以亚毫秒计 | 并发调度改变不了瓶颈位置；单实例模型本来就是串行吞吐上限 |
| 使用场景 | 单机单用户；多符场景由太极 DAG 承担，且设计上就要求**确定性**（拓扑层序、层内字典序、可复现回执） | 并发会引入非确定性 interleaving，与「同一张图永远得到同一张回执」直接冲突 |
| 资源预算 | 2B 级本地部署目标低内存（≤4 GB 档）；async 运行时 + 任务抽象带来常数级内存与依赖面增量 | 无吞吐收益却增加依赖与内存，违背 8.10 预算 |
| 安全审计 | 串行单流让缴符事件链天然线性，无并发写竞争；缴符是 append-only 安全审计面 | 并发写需要锁/分片，扩大审计复杂度与出错面 |
| 逃生通道 | provider / 工具注册 / 编排执行器都是 trait（`NodeExecutor`、`Provider`、`Confirmer`） | 若未来真需要并发（如远程 provider 池），只替换适配层即可，不需要改架构 |

### 22.2 量化基准的边界（不编造）

「实测吞吐对比」需要真实模型：mock provider 下的数字只测得出亚毫秒级的框架开销，没有决策价值。因此量化基准**随 T23（真机端到端验收）一并补**：届时若真机数据显示单实例模型在并发下有显著吞吐收益（且太极的确定性约束仍可保持），再重开此项；在那之前同步是定案。

### 22.3 顺带修正（T12）

`fulu init` 原文案自称「走成符→盖印→dry-run→确认的完整仪轨」，实际只完成零模型四步（采集 / 发现 / 预览 / 生成示例符），属于不实表述。已改为如实标注：本命令是零模型准备（预览），不焚符、不写缴符；示例符由用户显式 `altar dry-run` → `--confirm` 才走完整仪轨；对话式引符需真机权重、当前未实现。

## 24. M4 发布流水线（T26–T31，2026-11-11）

发布链路此前只有「zip / tar.gz + SHA256SUMS」，安装包、签名、SBOM、审计全部缺位。本节记录补齐后的形态与**明确的验证边界**。

### 24.1 产物矩阵（T26）

| 平台 | 产物 | 实现 |
|---|---|---|
| Windows x64 | `.zip`（便携）+ `.msi` | WiX 3（`packaging/windows/fulu.wxs`）：perUser 安装到 `%LOCALAPPDATA%\fulu`，只往**用户 PATH** 追加；`candle` / `light` 缺失即判失败，不产假安装包 |
| macOS (arm64 / x64) | `.tar.gz` + `.dmg` | `Fulu.app` 包（`packaging/macos/Info.plist`，`CFBundleExecutable = fulu-ui`）+ `hdiutil create -format UDZO` |
| Linux x64 | `.tar.gz` + `.deb` + `.AppImage` | `.deb` 用 `dpkg-deb --root-owner-group`，`Depends` 写明 X11 运行库；AppImage 用 `appimagetool`（先 `--appimage-extract` 规避 FUSE），图标由 CI 内 Python 现场生成 256×256 PNG |

**AppImage 是 best-effort**（`continue-on-error: true`）：它额外依赖外网下载 `appimagetool`，失败时**不产出**该文件并留下 `::warning::`，绝不生成一个空壳冒充成功。

### 24.2 签名与公证（T27）

原则：**有凭据才签，没凭据必须明说**。

- Windows：读 `WINDOWS_CERT_PFX_BASE64` + `WINDOWS_CERT_PASSWORD`，用 `signtool /fd SHA256 /tr ...` 签 MSI 与两个 exe；
- macOS：读 `APPLE_CERT_P12_BASE64` / `APPLE_CERT_PASSWORD` / `APPLE_ID` / `APPLE_TEAM_ID` / `APPLE_APP_PASSWORD`，`codesign --options runtime --timestamp` + `notarytool submit --wait` + `stapler staple`；
- **缺任一凭据**：写入 `UNSIGNED-<target>.txt` 随发布资产上传，同时打 `::warning::`。发布页因此不会出现「看起来签过名」的错觉。

### 24.3 SBOM 与依赖审计（T28 / T29）

- `sbom` job：`cargo install cargo-cyclonedx --locked` → `cargo cyclonedx --format json --all` → 全仓库 `*.cdx.json` 打成 `taoism-agent-sbom-<tag>.tar.gz` 上传；一个都没生成则判失败（不吃空包）。
- `audit` job：`rustsec/audit-check@v2`。与 `cargo-deny` 的 advisories 并行保留——两者数据库口径与抑制机制不同，宁可重复也不要漏。
- 按 docs/03 第 1 节第 6 条：**不允许 `ignore` 静默放过**，确需忽略必须登记理由与复审日期。

### 24.4 CI 矩阵（T30）

- `quality` 增加 `macos-15-intel`（x86_64-apple-darwin）——Intel Mac 仍在服役，不能只验 ARM；

### 24.5 清单闸门（T31）

`check_model_manifest.py` 两处收紧：

## 25. S6 符箓台完善（T33 / T34 / T35，2026-11-11）

| `skills_listing()` | 返回（已发现技能, 问题项）二元组 | 只读展示，**不安装不升级** |
| `risk_overrides_listing()` | 返回（覆盖条目, 问题项）二元组 | 只读展示，写入仍走 `fulu mcp risk set` |
| `AltarSession::replay_audit(&path)` | 逐行读缴符 JSONL | 只读、忽略空行、原样返回，**不校验链** |

`replay_audit` 刻意不做链校验：链校验属缴符写侧职责（写入时算摘要），读侧再算一遍只会给出「文件被改过」的模糊结论，而真正需要的是「哪一行坏了」。因此读侧只负责把内容交出来，判断交给使用者和未来的 `fulu audit verify`。

### 25.2 存符与字段表单（T33）

- **保存 = 按规范格式重写**：注释、字段顺序、空行都会丢。UI 在保存按钮旁直接写明这条，不做事后解释。
- 文件名校验：拒空名、拒路径分隔符、拒 `..`；缺省补 `.fu`；同名文件需勾「允许覆盖」。
- 保存前先 `parse_fu` 再 `dump_fu`——**写得出来必须先读得回去**，语法错在保存时就被挡住，不会落一个坏文件。
- 表单改字段后 `apply_form()` 走 `dump_fu` 回写并 `invalidate()`：符文变了，之前的 dry-run 结果立即作废（与 CLI 破符语义一致）。表单只覆盖常用字段（符名 / `model_id` / 沙箱 / 步数 1..=64 / token 256..=200000 / 目标 / 判据），其余字段保留原文——**不做「表单即全部」的假象**。

### 25.3 模型与法坛面板（T34）

### 25.4 设置面板（T35）

全部**只读**：提示词档位（`full / minimal / none` 三选一可切）、IP 粗粒度开关、会话头预览、七层提示词预览（截前 8000 字符）、符胆摘要、技能清单、风险覆盖表。切换档位与开关只改内存态，落盘仍由配置文件负责——**GUI 不写全局配置**，与「外宗/技能包只展示不管理」同一条原则。

## 27. T39 中文 DSL / `.fub` / 复文 / 云篆实施补记（2026-11-11）

方案级的取舍记在 `docs/03` 第 7 节；本节只记落地形态与验证边界。

### 27.1 `fulu-script` 从「一层 JSON」变成「四块」

| 模块 | 职责 | 关键常量 |
| --- | --- | --- |
| `dsl.rs` | 中文 DSL 编解码（`fulu fu dsl`、`fulu convert --to dsl`） | 18 个必填键、3 个可重复键（`工具`/`召将`/`符胆`）、5 条分组行 |
| `fub.rs` | `.fub` 二进制信封（`fulu fu pack/unpack/info`） | `FUB_MAGIC = b"FUB\x01"`、`FUB_VERSION = 1`、`FLAG_FOLDED = 0b1` |
| `fuwen.rs` | 复文：常用片段的短代号字典 | `FUVEN_VERSION = 1`、`ESCAPE = 0x01`、`DICTIONARY` 24 条 |
| `yunzhuan.rs` | 云篆：只做**版式与笔顺描述**，不做渲染 | `CloudLayout`（千分比）、6 种笔画基元（横竖撇捺折点） |

`fulu-app` 侧只加了一个入口 `load_fu_file(path) -> (Fu, FuForm)`（`FuForm::{Json, Dsl, Fub}`），
`load_fu` 改为委托它；CLI / GUI 都走这一个门面，避免「命令行能烧 DSL、界面只认 JSON」的分叉。

### 27.2 三条不能含糊的设计口径

1. **DSL 是语法，不是第二套语义。** 符印始终由 `canonical_bytes`（紧凑 JSON）计算，DSL 只是同一棵树的另一种写法。实机验证：同一张符的 JSON / DSL / `.fub` 三种形态 `fu seal` 全部输出 `ffe9c014…86e9fc`。若哪天 DSL 自带一套哈希，`seal_is_identical_whether_written_as_dsl_or_json` 会立刻变红。
2. **`.fub` 只信重算，不信文件头。** 解码顺序是「展开复文 → 解析 → 重算 canonical → 比对 32 字节符印 → 比对符名」；文件头那 32 字节只当**待验证的断言**用。为此专门锁了一条最像真货的伪造：`a_valid_body_with_a_stale_seal_is_rejected`（正文合法、符印是旧的）。严格模式同时拒绝多余尾部字节、未知版本、未知折叠标志、字典版本不符（`stale_fuwen_version_is_refused_rather_than_misdecoded`）——宁可读不出来，也不猜。
3. **云篆只交描述，不交像素。** `describe(fu)` 产出「符头/符胆/符脚 三段各占多少千分比、每行几字、笔画基元如何归一化到 0..=1000」，符胆按字符数折行、超 `max_lines` 截断并置 `truncated`。渲染归 T36；数据层先定死，免得 UI 自己发明排版规则。

### 27.3 复文的取舍：不吹压缩比

`fold` 用**最长优先**匹配把常用长片段换成 `0x01 <code>`，`unfold` 反向还原，`0x01 0x01 0x00` 这类边界有往返测试兜住。实测示例符：正文 821 字节 → 716 字节（约 −13%），`fu pack` 把这行如实打印出来并说明采用了哪一种，不做「压缩率 X:1」的营销话术。字典只有 24 条且带版本号：改字典就必须升 `FUVEN_VERSION`，否则旧 `.fub` 会被拒而不是被解错。

- 全量 **311 个测试零失败**；`fmt --check`、`clippy --workspace --all-targets -D warnings` 全绿；`cargo deny check` 四项 ok（`advisories / bans / licenses / sources`）。
- 相对 T40 基线（268）新增 43 项：`fulu-script` 37（DSL 13 / `.fub` 11 / 复文 6 / 云篆 7）、`fulu-app` 2（形态识别与拒收垃圾）、`fulu-cli` 3（形态识别不靠扩展名、三形态同符印、二进制必须有落点）、`fulu-ui` 1（工作区扫描只列三形态）。
- 真机验证（Windows）：`fu dsl` 输出可读中文 DSL；JSON→DSL→`.fub` 三形态符印一致；`fu pack` 报「未折叠 821 / 折叠 716，采用复文折叠」；`fu info` 只读文件头并明确标注「文件内记录，info 不校验」；`fu unpack` 正常解出，正文改一字后 `exit=1` 报破符；`altar dry-run` 对 `.dsl` 与 `.fub` 都成功且符印一致。

### 27.5 残留问题（明示）

- **`.fub` 无签名。** 符印是哈希：能防篡改，不能证明「谁写的」。伪造一张自洽的符（正文 + 自算符印）完全可行，`.fub` 只保证「读出来的就是写进去的」。身份签名仍挂在 T27 密钥链上，未做。
- **复文字典不通用。** 24 条片段是给「符箓自己的固定句式」用的，不是通用压缩器；换一批文案收益会掉，别把它当 gzip。
- **DSL 表达力有限。** 只有 `键 值`、分组行、`符心/符事` 两个多行块；块内每行必须缩进两格，不能嵌套块，也不支持字段级注释（`#` 必须整行）。
- **GUI 保存仍是规范 JSON。** 从 `.dsl` / `.fub` 载入后编辑器里是**规范文本**，原文件不会被回写；`.dsl` / `.fub` 的产出仍要显式跑 `fulu convert` 或 `fulu fu pack`。

### 29.2 四条不妥协的语义（与设计稿逐条对应）

1. **流式不改变仪轨**：`invoke_stream` 返回完整 `InvocationReply`，工具调用全部收齐后才过箓与敕门。
   单测 `streaming_is_display_only_and_never_changes_the_receipt` 锁定「回执与不流式时完全一致」。
2. **半途失败即整轮失败**：没有 `[DONE]` 就报 `Protocol("流在结束标记 [DONE] 之前中断…")`，
   不拼半份回执；已收字数进缴符事件（`流式中断：已收 N 字符，仅记账不回喂模型`）。
3. **取消即释放**：`Cancel` 之后连接立即关闭，返回 `Cancelled`；新终态 `TalismanState::Cancelled`
   （「中止」）与 `EventKind::Cancelled`（「取消」）——**不冒充炸炉，也不冒充成功**。
4. **不静默退化**：装了 sink 但 provider 不支持流式 → 显式报错，不偷偷改成整块返回。

## 32. moli 无头浏览器必须独立 profile（2026-11-11，写验收清单时撞出来的真实缺陷）

### 32.1 怎么发现的

准备 T38 的「符箓台人工验收清单」时跑全量测试，`moli_end_to_end_with_real_browser_when_available`
第一次失败；单跑通过，连跑 5 轮错 1 轮。失败时断言打出 `DOM 0 字节 / 抽文 0 字`，
而 `open_with_browser` 并没有报错——说明浏览器**退出码是 0**，只是什么都没输出。

### 32.2 根因

本机当时有 **41 个 `msedge.exe`**（用户开着 Edge）。Chromium 系浏览器对同一个
`user-data-dir` 只允许一个实例：第二个进程会把命令行请求转交给已有实例，然后自己
**exit 0 退出**。于是：

- `output.status.success()` 为真 → 不进错误分支；
- stdout 为空 → `html_to_text` 得到空串 → 集成测试断言失败。

这不只是测试问题。真实使用时「用户开着浏览器」是常态，`moli.open` 会返回空正文，
而第 23 节的容错设计本意是「页面无可见文本要如实报错」——现在连那一步都到不了，
属于**静默失败**，比报错更糟。

### 32.3 修法

| 位置 | 改动 |
| --- | --- |
| `open_with_browser` | 每次调用生成 `fulu-moli-profile-<pid>-<毫秒>` 临时目录，传 `--user-data-dir=`；另加 `--no-first-run --no-default-browser-check`。先 `remove_dir_all` 再判错（浏览器没起来时 profile 常已被创建一半） |
| `moli_headless_args` | 参数表抽成纯函数，便于测试；`moli_headless_args_always_isolate_the_profile` 断言必须有 `--dump-dom`、`--virtual-time-budget`、非空 `--user-data-dir=` |
| 集成测试 mock | 服务端从「只 accept 一次」改为非阻塞循环 accept（5ms 轮询 + 停止标志）。浏览器打开一个页面会发起不止一个连接（预连接 / favicon / 重试），只接一次会让真正的页面请求落空——这是另一半 flaky 来源 |

为什么不用 `#[ignore]` 或加重试：那只是把静默失败藏起来。根因是「拿不到 DOM 却当成功」，
应该在拿的地方修，并用测试锁住参数，防止以后有人把 `--user-data-dir` 当冗余删掉。

### 32.4 验证

- moli 真机集成测试连跑 **10 轮零失败**（修前 5 轮错 1 轮）。
- 全量 `cargo test --workspace` 连跑 2 轮，各 **341 项零失败**（新增 1 项参数断言）。
- `cargo clippy --workspace --all-targets -D warnings` 退出码 0；日志里的 29 条 warning
  全是沙盒「删除增量编译锁文件失败（os error 5）」的噪音，与代码无关（逐条对应，非 lint）。
- **未验**：macOS / Linux 的浏览器路径（候选表里有，但本机没有那两个系统）；
  用户实机开着 Chrome 时的表现（Windows 已覆盖，Edge 与 Chrome 同源）。

### 34.1 先修的错误类型：取消曾被当成「炸炉」

`ritual.rs` 里取消走的是 `RitualError::Provider(detail)`（第 541–553 行）。后果：

- `Display` 打出「炸炉 · 推理失败：焚化被取消（…）」——**人按了中止，界面说炸炉**；
- `AppError` 把 `RitualError` 一律拍平成字符串（`AppError::Ritual(err.to_string())`），
  界面层拿不到任何可 match 的区分，只能去字符串里找「取消」两个字。
  这种「靠文案判断状态」的写法，改一次措辞就全线失灵。

修法是把终态贯彻到错误类型，与状态机一一对应：

| 层 | 新增 | 文案 |
| --- | --- | --- |
| `fulu-runtime::RitualError` | `Cancelled(String)` | `中止 · 调用方取消：{msg}` |
| `fulu-app::AppError` | `Cancelled(String)` | `中止：{msg}` |
| `From<RitualError> for AppError` | 特判 `RitualError::Cancelled` → `AppError::Cancelled`，其余仍走 `Ritual(string)` | — |

不变量：**取消不是故障，也不是过坛**，所以它既不能落 `Provider`，也不能落 `Timeout`。

### 34.2 GUI 的中止按钮

- 旗标：`cancel_flag: Option<Arc<AtomicBool>>`，焚符线程持有 clone，**每个流事件都查一次**
  （不只在文本增量上查，否则工具调用增量与 usage 阶段按不动）。
  置真后 sink 返回 `StreamControl::Cancel` → provider 立刻关连接 → 法坛落 `Cancelled` 并记账。
- 按钮出现在「焚符中……」那一行，按下后原地变「已请求中止……」并禁用（不重复置旗标）。
- **顺带把正在等的敕门卡片按「敕否」答掉**：否则焚符线程阻塞在 `ChannelConfirmer` 上，
  旗标永远没机会被读到。答否之后模型会换一条路再请一次，那次调用的第一个事件就会命中旗标。
- 完成后状态栏写「已中止（不是炸炉）· … 已收 N 字只记账不回喂；召将副作用不回滚」，用 `Tone::Info`
  而不是 `Tone::Bad`：中止是用户的决定，不是系统故障，但也不是成功（不给绿色）。

### 34.3 能力边界（界面上写死，不许含糊）

1. **只置旗标，不杀线程**——法坛要自己把 `Cancelled` 写完缴符再退出，硬杀会留下没落账的半张符。
2. **下一个流事件到达时才生效**。模型还在「想」、一个增量都没吐时按下，界面立刻变「已请求中止」，
   但要等第一个事件才真正断开。这是流式协议的固有限制，不是实现偷懒。
3. **取消 ≠ 回滚**。已经执行过的召将副作用不会消失，缴符里的事件也照旧在。
4. provider 不支持流式时不会走到这里：`ignite_with_stream` 会直接报「该 provider 不支持流式」，
   `call_count()==0`，不存在「按了没反应」的僵死态。

### 34.4 测试

| 测试 | 断言什么 |
| --- | --- |
| `cancelled_ritual_error_stays_distinguishable_through_app_error` | `RitualError::Cancelled` → `AppError::Cancelled`，文案以「中止：」开头；对照组 `Provider` 仍是 `Ritual` 且含「炸炉」 |
| `cancelling_mid_stream_lands_in_cancelled_and_records_it`（改） | 终态 `Cancelled` + 事件 `Cancelled` + 记账已收字数；**错误变体必须是 `RitualError::Cancelled`**，文案不许以「炸炉」开头 |
| `cancelling_during_tool_call_delta_executes_no_tool`（新） | 在工具调用增量处取消：**缴符里不得出现 `ToolResult`**（收一半的召将不许执行）、终态取消、`call_count()==1`（取消不是故障，不自动重试） |

## 35. 性能预算实测基线（T32，2026-11-11）

### 35.1 为什么现在才做

9.3 写着「空闲内存 ≤ 80 MB｜冷启动 ≤ 1.5 s｜轻量发布包 ≤ 20 MB｜单符校验 ≤ 5 ms」，
并注明「M1 起实测校准」。实际一路做到 M3 都没校过——**这类数字只要没人测，就会变成
评审时的装饰**。本节把四个指标全部测掉，并明确哪个达标、哪个不达标。

### 35.2 测试环境

Windows 10 专业版 22H2（build 19045.6456）、Intel/AMD x64、GTX 1050 Ti、物理内存 15.9 GB（可用 6.2 GB）、
`--release` 与 debug 各测一次、提交 `f44da9f`、测量时间 2026-11-11 13:5x（本机交互会话，无其他重负载）。

测量方法（可复现，不用 instrumentation）：

| 指标 | 方法 |
| --- | --- |
| 二进制体积 | `stat -c%s`；压缩体积用 `zstd -19` |
| 启动到出窗 | 先起一个 10 ms 间隔的观察者轮询 `Get-Process` 的 `MainWindowHandle != 0`，**再**启动进程，取 `now - StartTime`（先起观察者是为了不把「采样晚了」算进启动时间） |
| 空闲内存 | 进程稳定 20 s 后读 `WorkingSet64` / `PrivateMemorySize64` / `PeakWorkingSet64`，98 s 复测一次确认不增长 |
| CLI 峰值内存 | 5 ms 间隔轮询所有 `fulu` 进程取最大值，期间连跑 8 次 `altar run`（打真实回环 mock，完整焚符） |
| 单符校验 | 进程内临时 example 跑 2000 次 `inspect_fu`（解析 + sha256 重算）取平均，用完即删 |

### 35.3 实测结果

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 单符校验 | ≤ 5 ms | **0.019 ms**（2000 次平均） | ✅ 260 倍余量 |
| 冷启动（出窗） | ≤ 1.5 s | **44 ms**（release）/ **269 ms**（debug） | ✅ |
| CLI 启动（`fulu doctor`） | — | 84–90 ms（首次 291 ms，冷缓存） | ✅ 与单符校验同量级：时间几乎全在进程创建 |
| CLI 峰值内存 | ≤ 80 MB | **8.39 MB**（完整焚符，含 HTTP 与缴符） | ✅ |
| GUI 空闲内存 | ≤ 80 MB | **97.6 MB**（WS）/ **125.1 MB**（private）/ 峰值 100.3 MB | ❌ 超 22%（按 WS 计） |
| 二进制体积 | — | CLI **1.06 MB**、GUI **11.64 MB**（release）、GUI 40.26 MB（debug） | — |
| 轻量发布包 | ≤ 20 MB | **12.70 MB** 未压缩 / **6.65 MB** zstd（CLI + GUI） | ✅ 但这是二进制口径，安装包未构建（T26） |

### 35.4 80 MB 这条目标为什么不成立

先把话说清楚：**不是「优化一下就到了」，也不是「GUI 无所谓」**。现有证据能确定的只有三条：

1. **CJK 字体常驻 6.0 MB**：`NotoSansSC-Regular-gui.otf` 6.02 MB 经 `include_bytes!` 编进二进制，
   运行期解压驻留（`fulu-ui/src/fonts.rs`）。这是为了「三平台中文不缺字」付的确定成本。
2. **GUI 框架与显卡驱动占大头，但没拆开量**：一个 release 二进制 11.64 MB 的程序 idle 到 97.6 MB，
   差额不可能来自业务代码（缴符链、符文本都在 KB 级）。合理怀疑是 glow/OpenGL 上下文与
   显卡驱动（驱动侧的分配会计入进程工作集），**但这一条未拆解验证**，要拆得用 ETW / VMMap，
   本轮没做，所以只记「差额主要在 GUI 后端，未量化」。
3. **CLI 的 8.39 MB 说明预算本身没问题**：同一条业务链路在无 GUI 时非常轻。
   80 MB 这个数字当初是按「无 GUI 轻量包」定的（见 8.5 预算修正），拿它考核 GUI 属于**口径错配**。

### 35.5 修正后的预算（两档，按实测定，不按想象定）

| 档 | 指标 | 实测 | 阈值（含 30% 余量） |
| --- | --- | --- | --- |
| CLI（无 GUI） | 峰值内存 | 8.4 MB | **≤ 12 MB** |
| CLI | 冷启动 | 85 ms | **≤ 150 ms** |
| CLI | 单符校验 | 0.019 ms | **≤ 1 ms** |
| GUI（符箓台） | 空闲内存（WS） | 97.6 MB | **≤ 130 MB** |
| GUI | 出窗时间（release） | 44 ms | **≤ 500 ms** |
| 发布包 | CLI + GUI 二进制合计 | 12.7 MB / 6.65 MB 压缩 | **≤ 20 MB 未压缩** |

9.3 的 80 MB 一条改为「CLI 档 ≤ 12 MB；GUI 档单独计，≤ 130 MB」——**改数字不是为了让指标好看，
是因为原来那个数字从来没被任何一次测量支持过**。如果将来要做「低内存模式」，
可行的方向是字体按需加载（不 `include_bytes!` 全量）与不做 OpenGL 上下文的重绘，
但那属于新特性，不在本轮范围。

### 35.6 未做

- **首帧绘制时间没测**：`MainWindowHandle != 0` 只能证明「窗口已创建」，不等于「画面已出来」。
  egui 首帧含字体图集构建，真实首帧一定比 44 ms 长；没有 instrumentation 就只能记「未测」，
  **不许用「窗口出来了」顶替「画面出来了」**。
- **macOS / Linux 全部未测**（缺硬件）。
- **安装包体积未测**（T26 只写了打包脚本，本机没有 WiX/hdiutil/dpkg，CI 未实跑）。
- 内存未做拆解（字体 / GL 驱动 / egui 各自占多少），所以只有「在哪」的定性判断，没有分摊表。
- 未做任何优化：本节只交付**基线**，不交付改进。

## 36. RetryPolicy 接网络（2026-11-11，收掉最后一块纯函数摆设）

`RetryPolicy` 从 T13 起就是纯函数（`backoff_millis` / `should_retry`），但**没有任何调用方**——
`invoke` 一发一收从不重试，且 `should_retry` 对 429/5xx 走 `_ => false`，注释自承「无法确定状态码」。
根子有两处：`require_success()` 产生的 `HttpError::HttpStatus(code, body)` 在 `invoke` 里被拍平成
`Transport(e.to_string())`，**状态码在映射时丢了**。本节把这条链修通。

### 36.1 错误分类

`ProviderError` 新增两个变体，映射在 `map_http_error`（不再拍扁）：

| 变体 | 来源 | 默认重试 |
| --- | --- | --- |
| `RateLimited(String)` | `HttpStatus(429, …)` | 开 |
| `ServerError { status, detail }` | `HttpStatus(code ≥ 500, …)` | 开 |

不重试的类别与理由（写进 `should_retry`，不许再出现 `_ => false`）：
`Cancelled`（人按停，重试=违抗调用方）、`Protocol`（格式错，重发大概率还错）、
`NotConfigured`（端点没设）、`ModelUnavailable`（服务没起，部署错误非瞬态，**不给「连不上就狂试」留口子**）、
`NotImplemented`、`BudgetExceeded`。

### 36.2 退避与抖动

- `LocalLfmProvider` 新增 `retry: RetryPolicy`（默认 3 次 / 400ms 基准 / 四类全开）+ `set_retry_policy`。
- `invoke` 与 `invoke_stream` 各套一层退避循环；jitter 用 `SystemTime` 纳秒做种子夹在 800‰..=1200‰，
  注释写明非密码学用途——**不引第三方 crate**（连 rand 都不要）。
- `http.rs` 一处语义修正：对端收下连接却一个字节不回就断开，原来报 `MalformedResponse("响应为空")`
  会被流式路径归为不可重试的 `Protocol`；现改为 `Io("连接在收到任何响应字节之前被对端关闭")` →
  `Transport` → 可重试。**收到过字节但格式坏**仍是 `Protocol`，语义未动。

### 36.3 不静默：重试必须可看见

- `InvocationReply` 加 `#[serde(default)] pub retries: u8`；`Receipt` 加 `retries_total`（聚合）。
- 缴符事件：`Invoked` 事件详情追加 `重试={N}`（`docs/03` 第 2.5 节「重试不许静默」的落地形态——
  计数随该次请神事件落账；provider 只报每次调用的聚合数，不区分第几次尝试，
  **逐次尝试各落一条事件需要 provider 回调钩子，本版没做**，如实记为未做）。
- CLI 回执多打一行「重试 N 次后成功」；GUI 缴符面板同样显示。CLI 加 `--retry N`
  （0..=10；N=0 映射 `max_attempts=1` 即关闭）。

### 36.4 流式的硬边界：首个增量之后绝不重连

流式只在**零增量**时可重试：一旦任何事件（含 `TextDelta`/`ToolCallDelta`/`Usage`/`Done`）交给 sink，
再失败就直接返回该错误。测试用 listener 计数证明第二个连接**从未被发起**——
这兑现 T13 设计里「首个增量后不可重试」的承诺（避免重复输出与重复计费）。

### 36.5 测试（`crates/fulu-provider/tests/retry_e2e.rs`，真实 TCP，退避 1ms）

| 测试 | 不变量 |
| --- | --- |
| `invoke_retries_on_server_error_then_succeeds` | 500×2 后成功：计数==3、`retries==2` |
| `invoke_respects_max_attempts` | 硬上限：计数==`max_attempts`，报 `ServerError` 且状态码保留 |
| `invoke_does_not_retry_rate_limited_when_disabled` | 关 429 重试 → 计数==1、立刻报 `RateLimited` |
| `stream_retries_before_first_event_only` | 零字节断开→重连成功：计数==2、`retries==1` |
| `stream_never_retries_after_first_event` | 首增量后掐断 → 报 `Protocol`（含「[DONE]」），第二连接从未发起 |

`ritual.rs` 补 `provider_retry_count_lands_in_audit_event_and_receipt`：
脚本回执 `retries=2` → 缴符 `Invoked` 事件含 `重试=2`、`receipt.retries_total == 2`。

### 36.6 未做 / 边界

- `--retry` 只透传 `max_attempts`，不暴露 `base_backoff_ms` / `RetrySet` 细项。
- jitter 种子是时钟纳秒，同一纳秒并发下抖动可能相同。
- 默认 400ms 基准未调小：重试只对回环本地服务触发，全量测试耗时无新增。
- 真实 `llama-server` 的 429/5xx 行为未验（仍缺权重）；重试与流式的组合只在假 SSE 服务上验过。

### 37.2 交互与语义（写死，不许含糊）

1. **一次性确认**：勾「我确认焚化整张符图（不可撤销）」才可点「焚化符图」；未载入 / 未勾选 / 焚化中三者任一都禁用。与 CLI 的 `--confirm` 同口径：编排器不替任何节点点头。
2. **载入即校验**：`load_taiji_graph` 失败（含环 / 未知依赖 / 重名 / 缺符文）把**错误原文**红字照抄展示，不改写、不吞掉。
3. **层视图只是展示**：`layers()` 算「第 1 层：a、b」给人看，执行顺序永远来自 `validate()`；有环时 `layers()` 整体 `Err`，不给半份分层。
4. **逐节点进度**：每个节点判定后（成功/失败/**跳过**）回调一次；跳过也带理由（「依赖未完成：a」/「总步数预算已耗尽」）。

## 38. 模型 bundle 分发合规自动化（T24，2026-11-11）

T24 的原始指控是两条：`model-bundle` job「必须在 Release 说明中标注 lfm1.0」**只是一行 echo**；
下载权重后从未与清单比对 sha256（清单里也还是 null，所以谈不上伪造，但等于没校验）。
本节把「合规」从注释变成**会拒绝执行的闸门**。

### 38.1 生成器：`.github/scripts/gen_compliance_notes.py`

纯标准库、无网络、确定性输出（同样输入两次字节相同，有测试锁住）。核心逻辑是可导入的
`check()` / `generate()`，`main()` 只做参数解析。四种模式与退出码：

| 模式 | 合法清单 | 缺字段 | sha256 为 null |

MIT/Apache 一类 → 直接拒绝（防止把权重标成宽松许可）。

## 39. M2.1 权重下载链路：`model seal` / `model fetch`（2026-11-12）

T20（摘要固化）与 T21（HTTPS 公网下载）合并落地。核心决策：**TLS 白名单唯一例外收敛进一个新 crate**。

### 39.1 `fulu-download`：最小 HTTPS/1.1 客户端

- 依赖三件套：`rustls` 0.23（ring provider）+ `rustls-pki-types` + `webpki-roots`（内嵌 Mozilla 根集，
  **不读系统证书库**，信任锚固定可审计）。新增许可见 `THIRD_PARTY_NOTICES.md` 第 3 节与
  `deny.toml`（CDLA-Permissive-2.0，webpki-roots 的根证书**数据**许可）。
- 手写 HTTP/1.1 GET：chunked / Content-Length / 读到连接关闭三种响应体模式，全部**流式**交给调用方
  落盘并同步算 sha256——1.1 GB 权重不进内存。
- 重定向最多 5 跳，**每一跳必须仍是 https**，降级明文一律 `RedirectInsecure` 拒绝；每跳落点记录进
  `redirect_hops`，下载回执里如实列出「到底连过谁」。
- 明文代理走 CONNECT 隧道（`--proxy http://127.0.0.1:7890` 或 `FULU_PROXY`），TLS 在隧道内端到端，
  代理窥不到内容；无代理则直连。
- 单行头 16 KiB / 头数量 128 / Location 2 KiB 上限，防恶意响应撑爆内存。
- **TLS 握手在 `open_tls` 里用 `complete_io` 循环驱动到完成再 flush**：握手未完成时
  write 的请求明文会停在 rustls 的发送队列（加密不了），直接 read 会干等响应直到
  超时——这是 rustls 的经典死锁，必须显式驱动。
- **对端不发 `close_notify` 直接关闭**：rustls 返回 `UnexpectedEof`。行读取与块读取
  都先重试一次拿 rustls 内部缓冲的剩余数据，再错/空才按 EOF 处理；完整性由
  Content-Length / chunked 终止标记 / sha256 校验兜底，最坏情况是如实报「被截断」，
  绝不静默通过半份数据。
- 职责边界：只服务模型下载链路，**不进符箓执行路径**；provider / moli / MCP 的回环链路保持明文。

### 39.2 两步闸门：先 `seal` 后 `fetch`

1. **`fulu model seal [槽位] --confirm`**（T20）：请求 HF tree API 元数据（KB 级，非权重），
   取 LFS 官方 `oid`（sha256）与 `size`；`--confirm` 后回写 `models/manifest.json`（自动备份
   `.bak`）。纯函数在 `fulu-model::seal`：oid 必须 64 位十六进制、非 LFS 明确拒绝、
   与已固化值冲突拒绝改写（幂等通过）。**写进清单的每个字节都来自上游，绝不编造。**
2. **`fulu model fetch [槽位] --i-understand-license [--proxy URL] [--resume]`**（T21）：
   三道闸门——许可显式确认、清单已固化（`verification_ready`）、槽位可运行；任一不满足都在
   **发起任何网络请求之前**拒绝（exit 2）。
   - 下载到 `<缓存>/<槽位>/<file>.part`，全程流式；断点续传：前缀哈希续算（`digest_file_state`
     返回未 finalize 的 `Sha256`，续算不重复读盘两遍）、Range 请求、服务器忽略 Range 返回 200
     时截断重来并明说、sha256/字节数**双校验**通过才原子改名落位。
   - 瞬态错误（Io/Connect/Timeout）重试最多 3 次，指数退避；协议/校验类错误**不重试**（重放
     坏数据毫无意义）。摘要不符即删断点文件，不留下无法校验的数据。
   - 回执列出实测字节、sha256、重定向跳数与许可链接。

### 39.3 诚实口径

- **清单口径已统一（2026-11-12 修复，见 §39.5）**：seal 写回的是**文件**清单，编译期内嵌快照不会自动更新；
  现在 `verify` / `list` / `import` / `doctor` / `model_status` 全部走 `ModelManifest::runtime()`（优先文件清单、
  文件损坏明确报错不静默回退、安装环境无文件时才回退内嵌）。清单未固化时 `fetch` 提示先 `seal`，
  与旧桩相比拒绝语义不变。
- 两个命令都是显式触发（用户敲命令 = 明确同意联网），`--confirm` / `--i-understand-license`
  分别守住写回与下载两个高危动作；没有后台重试、没有静默 fallback、没有自动更新。
- 分发端（T24）不变：bundle 仍要求清单已固化，`model-bundle` 作业在下载前就检查 sha256。

## 40. T22 `llama-server` 生命周期管理 + T23 真机端到端（2026-11-12）

T22 落地为新 crate `fulu-engine`（只依赖 fulu-model / fulu-provider，无 tokio，同步执行器口径不变）。
本机 llama.cpp 二进制与 1.1 GB 真实权重均就位后，T23 核心链路真机走通。

### 40.1 二进制获取与运行时核验

- llama.cpp Windows 预编译包 `llama-b12314-win-x64.zip` 经 7890 代理下载，zip 内 sha256 校验通过
  后解压到 `%LOCALAPPDATA%\taoism-agent\bin\llama-b12314\`（与权重一样**不进 Git**）。
- `discover_binary()` 扫描 bin 目录下 `llama-b<N>` 目录名，**按 N 数值**取最新（字典序会把 b9999
  判得比 b12314 大）；找不到才回退 PATH。`check_runtime()` 解析 `llama-server --version` 输出的
  build 号对 `min_runtime = llama.cpp >= b11960`；解析不到如实返回 `UNVERIFIED`，不猜。
- 实测 `--version` = `0.9.0-dev (build 12314, commit e1f7593c3)`。

### 40.2 生命周期设计（不静默启动 + 带核验的停止）

- `EngineConfig`：binary / model / port / context / idle_seconds / host / log_path；`model start`
  显式拉起（打印「仅 127.0.0.1，不联网、不下载」），**没有任何自动启动路径**。
- `EngineHandle`：spawn → 轮询 `/health` 到就绪（含 1.1 GB 权重加载，实测 3.15 s）→ 持有 child；
  前台常驻「回车退出 + 闲置自动退出」，Drop 回收。Windows spawn 带
  `CREATE_BREAKAWAY_FROM_JOB | CREATE_NO_WINDOW`；breakaway 被沙盒拒收时回退前**重挂 stdio
  日志文件**（stdio 已被 take，不重挂就丢日志）。
- `model start --detach` 写运行记录（pid / port / model / started_unix，原子写回）；`model serve`
  无记录时回退到环境端点探活。
- `model stop` **绝不读个数字就 kill**：端点回环校验 → `/health` 可达 → 端点上已加载模型与记录
  一致（llama.cpp 返回绝对路径，分隔符 / 大小写归一后比对），三关全过才 taskkill /PID（不带 /T，
  避免误杀进程树）。端口 3 秒内未观测释放会如实 WARN，不谎称干净。
- **死 PID 修复（实测暴露）**：进程已被外部杀死时端点不可达，旧逻辑卡在「拒绝按 PID 盲杀」，
  陈旧记录永远清不掉。现在先探 PID 存活：死了 = 没有可误杀的对象，直接清记录并回报
  `already_stopped`；活着才走三关核验。PID 查询失败时保守当作活着（fail closed）。

- **LFM3 空正文误判达标 → 已修（2026-11-13，见 §41.1）**：LFM3-1.7B 把思考放 `reasoning_content`，

## 41. 判据修复 + 状态摘要缓存（2026-11-13）

T23 实测暴露的两个「已知未修」在同日收掉，均为小口径修复，不动架构。

### 41.1 空正文不得判达标（fulu-runtime::converge）

- **问题**：`output.len <= N` 对空串数学上成立——LFM3 思考耗尽预算后正文是空串、
  思考在 `reasoning_content` 里，判据把空串判成 converged=true，「看起来完成了」。
- **修法**：`evaluate()` 的 `MaxLen` 分支加空正文守卫——trim 后为空且 `limit > 0` 时判
  `Pending("正文为空（可能思考耗尽预算）；上限类判据不接受空回执")`。这与「目标不可判定就
  等于没有目标」同一根红线：空回执不是有效回执。`output.len <= 0` 是显式要求空输出，
  如实放行；`Success` / `NonEmpty` / `MinLen` / `Contains` 本来就过不了空串，不动。
- 测试：`empty_reply_never_satisfies_an_upper_bound_criterion`（空串/纯空白均拒，非空行为不变）
  与 `explicit_zero_upper_bound_still_accepts_empty_reply`。

### 41.2 状态摘要按 path + size + mtime 缓存（fulu-model::digest_cache）

- **问题**：`status()` 每次全量 sha256，`model list` / `doctor` / GUI 启动都要重算
  1.1 GB（release ≈ 8.5 s，debug ≈ 92 s）。
- **修法**：新模块 `fulu-model::digest_cache`——`verify_file_cached()` 按「归一化路径 + 字节数 +
  mtime（秒+纳秒）」三元组命中 `<缓存>/digest-cache.json`（原子写回 tmp+rename）；未命中重算
  后写回。判据与 `verify_file` 共用单一事实源 `verify::judge()`，不复制两份。
- **诚实边界**：只有 `status()`（list / doctor / GUI）走缓存；**显式校验命令 `model verify`
  始终全量哈希**，不走任何缓存。缓存文件损坏、缺字段、mtime 早于 Unix 纪元一律按未命中
  处理（重算是安全方向的静默，不会把错摘要当通过）。已知残余风险如实记录：文件在 mtime
  粒度内被改写且大小不变时可能命中陈旧值；需要强制全量时设 `FULU_DIGEST_CACHE=0`。
- **真机实测（本机 debug）**：`model list` 首次 92.4 s（全量+写缓存）→ 第二次 **0.07 s**；
  `doctor` 92 s → **0.87 s**；缓存里 sha256 与清单固化值一致；`model verify` 全量 92 s 不变
  （符合设计）。release 预计 8.5 s → 亚秒。
