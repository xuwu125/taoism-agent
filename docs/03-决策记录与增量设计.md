## 2. T13 云端 provider / SSE 流式 / 能力协商（设计稿）

> **2026-11-11 更新**：其中「流式」与「能力协商」已按本稿落地（见 `docs/02` 第 29 节）；
> 「云端 provider」**仍未实现**，准入条件见第 9.2 节。本稿保留原样，作为实现的对照基线。

### 2.1 现状与边界

`fulu-provider` 目前只有 `LocalLfmProvider`：`std::net::TcpStream` 手写 HTTP/1.1，端点被 `Endpoint::parse` 限制在 `127.0.0.1` / `localhost` 明文回环，无流式、无重试、无证书概念。这是**有意为之的安全边界**，不是欠账。

T13 的目标是「先把扩展面设计清楚，再决定实现」，因此本轮**只定接口与语义，不改实现、不改边界**。

### 2.2 能力协商字段

```rust
pub struct Capabilities {
    pub streaming: bool,            // 已有：服务端是否支持增量返回
    pub tool_calls: bool,           // 已有
    pub local_only: bool,           // 已有：数据不出本机
    pub max_context_tokens: u32,    // 已有
    // 新增提案
    pub parallel_tool_calls: bool,  // 一次回复里多个 tool_calls 是否可并行执行
    pub json_schema_mode: bool,     // 结构化输出是否支持 json_schema（而非 json_object）
    pub vision: bool,               // 是否接受图像内容块（与 T18 上游配套）
    pub reasoning_blocks: bool,     // 是否返回独立 reasoning 文本（需在提示词层过滤）
    pub max_tools_per_request: u16, // 0 = 不限；用于箓层裁剪工具表
}
```

**兼容规则**：新增字段必须有 `Default`，旧实现通过 `..Default::default()` 保持编译；未知能力一律取**保守值**（`false` / `0`），绝不默认「支持」。

### 2.3 流式抽象

```rust
pub enum StreamEvent {
    TextDelta(String),
    ToolCallDelta { index: u16, id: Option<String>, name: Option<String>, arguments_chunk: String },
    Usage(Usage),
    Done { finish_reason: String },
}

pub trait Provider: Send + Sync {
    fn id(&self) -> &str;
    fn capabilities(&self) -> Capabilities;
    fn invoke(&self, req: &InvocationRequest) -> Result<InvocationReply, ProviderError>;

    /// 默认不支持流式：老实现无需改动。
    fn invoke_stream(
        &self,
        _req: &InvocationRequest,
        _sink: &mut dyn FnMut(StreamEvent) -> StreamControl,
    ) -> Result<InvocationReply, ProviderError> {
        Err(ProviderError::NotImplemented("streaming"))
    }
}

pub enum StreamControl { Continue, Cancel }
```

**关键语义（不可妥协）**：

1. **流式不改变仪轨**：`invoke_stream` 的返回值仍是完整 `InvocationReply`，工具调用必须**全部收齐后**统一过箓核验与敕门，绝不边流边执行。
2. **半途失败即整轮失败**：流断在中间不拼出「半个回执」；已收到的文本只进缴符事件（标注 `partial`），不回喂模型当成功。
3. **取消即释放**：`Cancel` 之后必须关闭连接并停止计费统计，`usage` 标 `estimated`。
4. **确定性**：同一请求两次流式调用的「事件序列最终归并结果」必须等价于非流式结果，用快照测试锁定。

### 2.4 SSE 解析口径

- 只认 `data:` 行；`event:` 仅用于区分 `ping` / `error`，不改变解析主路径。
- `[DONE]` 结束；空行是事件分隔，不是结束。
- `tool_calls` 按 `index` 归并增量（`id`/`name` 只在首个增量出现，`arguments` 逐段拼接），拼接结果必须能被 `serde_json` 解析，否则判 `Protocol` 错误而非猜测。
- 单事件上限 1 MiB、整轮上限 8 MiB（与 `MAX_RESPONSE_BYTES` 同源），超限直接断流。
- 服务端不返回 `usage` 时标 `estimated=true`，不伪称精确。

### 2.5 超时与重试（统一策略）

```rust
pub struct RetryPolicy {
    pub max_attempts: u8,        // 默认 3
    pub base_backoff_ms: u64,    // 默认 400，指数退避 + ±20% 抖动
    pub retry_on: RetrySet,      // Timeout / Transport / HttpStatus(429,500..=599)
}
```

- **只在没有产生任何可见副作用时重试**：非流式可重试；流式一旦发出首个 `TextDelta` 就**不可重试**（避免重复计费与重复输出）。
- 429 优先采信 `Retry-After`，缺失才用退避表。
- 每次重试必须落缴符事件（`retry` 计数），不静默重试。
- 重试总时长受符的 `timeout_secs` 硬约束，超出即 `Timeout`（过坛）。

## 3. T19 远程 MCP（HTTPS 边界）威胁模型与实现口径

### 3.1 为什么这是「安全边界变更」

原先的不变量只有一条：**fulu 只与回环地址说明文 HTTP**。它一次性消掉了整类风险——没有 TLS 就没有证书校验问题，没有公网就没有 SSRF、没有凭据外泄、没有中间人。放开远程 MCP 等于把这条不变量拆成一组需要逐条守住的新不变量。

### 3.2 资产与威胁

| 资产 | 威胁 | 缓解 |
|---|---|---|
| 用户 API token | 被写进符 / 配置 / 缴符 / 日志；被重定向到攻击者主机 | 只允许 `${ENV:VAR}` 引用；启动时解析、只在内存；缴符与日志统一脱敏；禁重定向 |
| 本地网络 | SSRF：借 MCP 访问内网 / 元数据服务 | 远程端点必须 `https://` 且主机命中 fulu 自有白名单；白名单**不接受 IP 字面量**与 `localhost` |
| 传输内容 | MITM / 降级 / 伪造证书 | 系统信任库校验（不提供 `--insecure` 开关）；`--proto =https` 禁降级；非 TLS 端口握手失败即报错 |
| 响应体 | 超大响应拖爆内存；恶意块 | 8 MiB 硬上限、60s 超时、64 KiB 正文截断、非文本块显式告警 |
| 审计链 | 密钥进事件 | `Authorization` / `Cookie` / `X-Api-Key` 等头部在落盘前脱敏，只记「N 个请求头」 |
| 模型 | 服务端内容提示注入 | 外宗输出一律是不可信文本；工具调用仍过箓 + 敕门，远程内容不能提升权限 |

### 3.3 实现口径（本轮落地）

1. **不引入 TLS 依赖**：HTTPS 交给系统 `curl`（Windows 走 Schannel/系统证书库，Linux/macOS 走系统 CA）。理由是 T14 moli 已验证同一条思路——把「首个 TLS 依赖例外」用「复用用户既有工具」消解，fulu 自身依赖树保持零 TLS。
2. **白名单文件**：`~/.fulu/remote-mcp.json`（fulu 自有，不碰任何 MCP 生态配置）：
   ```json
   { "allow_hosts": ["mcp.example.com", "*.trusted.dev"] }
   ```
   支持 `*.` 前缀通配（只匹配一级以上子域，不匹配裸域）；IP 字面量与 `localhost` 一律拒绝。
3. **凭据引用**：MCP 配置里的头部值可写 `${ENV:VAR}`；含敏感头部（`authorization` / `cookie` / `x-api-key` / `api-key`）却写成字面量的，**直接拒绝连接**并提示改用环境变量。
4. **传输硬约束**：`--proto =https`、`--max-redirs 0`、`--tlsv1.2` 起、`--max-time` 60s、`--max-filesize` 8 MiB。
5. **失败如实**：curl 退出码 + 首行 stderr 回传（不含头部值），绝不伪装成功。

### 3.4 残余风险（明示，不掩盖）

- 恶意 server 仍可返回带指令的文本——缓解是「它仍只是一条工具结果」，不获得任何额外权限。
- token 对 server 天然可见（协议要求）；只能保证它不出现在 fulu 的磁盘与日志里。
- 系统 `curl` 缺失或版本过旧时远程链路不可用：属于**如实降级**，不影响本地 stdio / 回环 HTTP。

## 4. T16 摄行电脑控制：权限与风险评估（写码前置）

### 4.1 能力定义（拟）

| 工具 | 动作 | 平台 |
|---|---|---|
| `shexing.type` | 向当前前台窗口输入文本 | Windows（SendKeys） |
| `shexing.key` | 发送组合键（如 `^s`、`{ENTER}`） | Windows |
| `shexing.click` | 移动光标并点击（左/右） | Windows |
| `shexing.screenshot` | 截屏写入工作区文件 | Windows |

### 4.2 风险判定

摄行是**全系统唯一能以「用户本人」身份操作任意窗口**的能力：它不受工作区路径约束，也不受命令行白名单约束。一次误操作可能删文件、发消息、点「确认」按钮。

因此分级为：

- **权限**：`Limited`（与其它内置工具同级，不新开权限档），但**默认不注册**——不开启时工具在名册里根本不存在，模型连看到的机会都没有；
- **风险**：`Destructive` + `EveryCall`（每一次调用都必须人点头，**不允许**用 `--allow-risk destructive` 批量预授权，也不允许「每符一次」）；
- **双重解锁**：环境变量 `FULU_ALLOW_SHEXING=1`（进程级）+ CLI `--shexing`（会话级）。任一缺失即不注册，理由是「最高权限要两把钥匙」；
- **参数全量展示**：确认页必须显示将输入的**完整文本**、坐标、目标文件路径，不允许「略」。

### 4.3 审计与限额

- 每次调用（含被拒）落缴符事件：动作类型、参数字节数、结果、耗时；截屏事件不落图片内容，只落路径与字节数。
- 配额：每符 20 次（防止模型陷入无限点击循环）。
- 截屏只能写入工作区（复用 `resolve_workspace_path`），不联网、不进提示词（除非用户显式把文件喂回去）。

### 4.4 残余风险与结论

- 无法阻止「用户点了确认但没看清参数」——只能靠确认页把参数展示到最完整；
- 无法阻止目标窗口本身是恶意程序；摄行不引入新漏洞，只是把用户已有的风险转成可审计的操作；
- **结论**：按 M4 交付，默认关闭、逐次确认、Windows 优先；跨平台（macOS Accessibility / Linux xdotool）单独立项，不在 v0.3 范围。

## 6. T40 箓牒（凭据库）：方案取舍与残余风险（2026-11-11）

### 6.1 要解决的问题

在 T40 之前，`credential_ref` 只是一个**受箓白名单里的字符串**：`fulu-register` 会核验「这条引用有没有受箓」，但**没有任何代码真正去取密钥**。于是有两个未闭合的缺口：

1. 云端 provider 一旦接上（T13），密钥从哪来；
2. 「符内绝不写密钥」这条红线，只靠成符阶段的字面量扫描（`looks_like_secret`）把关，**运行期无凭据可依**。

T40 补齐的正是这一段：新增 `fulu-vault`（代号「箓牒」），把「引用 → 密钥」的解析做成受控、可审计、可失败的一步。

### 6.2 两条路线，选了「委托系统工具」

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 链接原生 SDK（`keyring` crate / Win32 `CredRead` / libsecret） | 能力强，但 Windows 要 `windows-sys` + `unsafe`，Linux 要 dbus / 静态链接 libsecret，三平台各一套 | **否** |
| 委托系统自带工具（本方案） | 要求目标机器有对应工具；缺失时如实报错并指路 | **采纳** |

理由与 moli 复用系统浏览器、T19 复用系统 `curl` 做 TLS 校验是同一条：**不把平台 SDK 拖进依赖树**，也不让 `unsafe` 蔓延。代价是「工具不在就不可用」，而这恰好可以被**文件后端**兜住。

### 6.3 后端矩阵

| 平台 | 工具 | 取 | 存 | 删 | 密钥是否进 argv |
| --- | --- | --- | --- | --- | --- |
| Windows | `powershell.exe` + WinRT `PasswordVault` | 脚本常量、引用名经环境变量 | **stdin** | 脚本常量 | 否 |
| macOS | `security` | `find-generic-password -w` | `add-generic-password -U -w <密钥>` | `delete-generic-password` | **是（已登记为残余风险）** |
| Linux | `secret-tool` | `lookup` | `store`（**stdin**） | `clear` | 否 |

Windows 侧脚本是**常量字符串**，用户提供的引用名只经 `FULU_VAULT_USER` 环境变量传入，因此不存在引号/换行注入面；有测试锁住「脚本里不出现 ref、不出现格式化占位符」。密钥一律不进环境变量（同用户可读 `/proc/self/environ`）。

### 6.4 文件后端：为什么新增密码学依赖

系统凭据库在 headless Linux、CI、受限 Windows 上都可能不可用，需要一个可搬运的兜底。**手写密码学是错的**，因此引入 RustCrypto：

- `chacha20poly1305` 0.10（AEAD，MIT OR Apache-2.0）
- `pbkdf2` 0.12 + 既有 `sha2`（KDF，MIT OR Apache-2.0）
- `zeroize` 1（密钥清零，MIT OR Apache-2.0）

边界声明：**只用于「系统凭据库不可用」时的加密落盘，不参与任何网络握手**；TLS 依旧零依赖（远程 MCP 走系统 `curl`）。`cargo deny` 与 `cargo audit` 均覆盖这三个 crate，本机实测四项全绿。

参数：PBKDF2-HMAC-SHA256 **600000** 次、16 字节随机盐、ChaCha20-Poly1305 12 字节随机 nonce、**AAD 绑定引用名**（把 `cloud.cred` 改名成别的名字也解不开）。

落盘格式（UTF-8 文本，便于人眼确认「这里面确实没有明文」）：

```text
fulu-vault-v1
ref lu://default/cloud
kdf pbkdf2-sha256:600000
salt <32 hex>
nonce <24 hex>
ct <hex 密文 + 16 字节 tag>
```

另有两条防护：读取时把 `kdf` 行声明的迭代次数**夹到 `[1000, 10_000_000]`**（畸形文件不能把进程算死）；写盘先写 `.tmp` 再改名（中途失败不留半个密文），Unix 下目录 `0700`、文件 `0600`。

### 6.5 语义：箓牒里有这条引用 = 已受箓

`fulu-register` 的 `grant_credential` 此前没有任何调用者，`lu://default/local` 之外一切引用都会被驳回。T40 定下的规则：

> **`AltarSession::use_vault()` 把箓牒里登记的引用逐条写进名册**，因此「库里有」等价于「已受箓」。

这样不需要再引入一份新的授权配置文件，也不会出现「授权与凭据两处不一致」。反过来，`vault rm` 之后引用不再受箓，引用它的符会被驳回（CLI 输出里明说这一点）。

### 6.6 闸门顺序：破符 → 凭据 → 授箓 → 其余

`AltarSession::dry_run` 现在先做 `fu.validate()`，再做凭据解析，最后才进法坛的 `prepare`（其中含授箓核验）。理由：

- 结构都不对的符，谈凭据与授权没有意义；
- 凭据问题比笼统的「未受箓」更好定位——在 6.5 的规则下，补救动作就是 `fulu vault put <引用>`，错误信息直接给出该命令。

`ignite` 侧的红线：**没 `confirmed` 就一个字都不碰凭据库**。有计数测试锁住「dry-run 取 1 次、未确认时仍是 1 次、确认后恰好 2 次」。

### 6.7 已知残余风险（不遮掩）

1. **macOS 的 `security add-generic-password` 只能从 argv 收密钥**，同用户下 `ps` 可见。缓解：文档明示、优先建议在 macOS 上用 Keychain Access 手工存入，或改用文件后端。这是本方案唯一一处「密钥短暂出现在进程参数里」。
2. **Linux `secret-tool` 依赖 D-Bus 会话**，headless / 容器里会失败。失败时如实报 `BackendUnavailable` 并提示改用 `FULU_VAULT_PASSPHRASE`，**不会**偷偷写到明文文件。
3. **`FULU_VAULT_PASSPHRASE` 是环境变量**，同用户可见。这是「非交互场景必须给出一个入口」与「不落明文」之间的妥协；交互式输入尚未实现，登记为后续项。
4. **系统凭据库无法枚举**（三平台都没有可移植接口），`list` 读的是只含引用名的 `~/.fulu/vault-index.json`；索引在 ≠ 密钥可取，`get` 仍可能 `NotFound`。文件后端则直接枚举磁盘目录，比索引可信。
5. **Windows `PasswordVault` 在无用户会话的服务上下文可能不可用**，此时报 `BackendUnavailable`。

### 6.8 本轮实机验证（Windows，`x86_64-pc-windows-msvc`）

| 场景 | 结果 |
| --- | --- |
| 文件后端 `put` → 落盘 → `get` | 通过；`.cred` 文件里 `grep` 不到密钥与口令（0 命中） |
| 口令错 | `无法解密：口令不对，或文件被改过（AEAD 校验失败）`，退出码 1 |
| 把密文换到别的引用名下 | 拒绝（AAD 绑定生效，单测覆盖） |
| 系统凭据库 `put` → `get --reveal` | 通过，取回值与写入完全一致（跨进程，非内存残留） |
| 系统库条目的位置证明 | 换一个 `FULU_HOME` 仍能取到 → 密钥确实在 OS 库，不在路径下 |
| 明文零落盘 | `FULU_HOME` 下只有 `vault-index.json`（仅引用名），全目录 `grep` 密钥 0 命中 |
| `vault rm` 后 | 取不回（退出码 1），`list` 为空；测试条目已清理 |
| 云端符无凭据 `altar dry-run` | 拒绝并给出 `fulu vault put` 指引，退出码 1 |
| 已存凭据 `altar dry-run` | 通过，确认页写明「已从箓牒取出（焚化时作为 Bearer 注入）」 |

未做：macOS `security` 与 Linux `secret-tool` 两条分支**未在真机执行**（本机只有 Windows），只验证了命令构造与解析（单测断言密钥不进 argv、退出码映射、脚本常量性）。这一条如实登记，不写成「三平台已验」。


## 7. T39 符文三形态（JSON / 中文 DSL / `.fub`）：取舍与边界（2026-11-11）

### 7.1 为什么要三种形态，而不是「统一成一种」

三种形态服务三种不同的人：

- **JSON（`.fu`）**：权威形态。评审、diff、手改都靠它；`canonical_bytes` 就是它，符印由它算。
- **中文 DSL**：写给人看、也写给人改。`符心` / `符事` / `捆仙绳` 这些词本身就是文档，不必先读 schema 才能改一张符。
- **`.fub`**：给传输与归档。紧凑、带自校验、一眼看出「这不是文本」。

不合并的理由：合并意味着其中一方必须妥协——要么人能读但要忍受二进制不便，要么机器友好但没人愿意手写。三种形态各自最优，代价是**必须有一个统一的识别入口**，否则迟早分叉。这就是 7.6。

### 7.2 DSL 是语法层，不是语义层

**决策**：DSL 只改变「怎么写」，不改变「是什么」。符印、校验、授权、缴符全部基于 `Talisman` 结构体，DSL 解码后得到的就是同一个结构体。

为什么这条要写进决策记录：一旦让 DSL 拥有自己的哈希或自己的默认值规则，同一张符就会有两种「身份」，`dry-run` 显示的符印和 `ignite` 时重算的符印可能不一样——而这正是「盖印后改符即破符」机制要防的事。

**接受的代价**：DSL 无法表达 `Talisman` 之外的东西（比如宏、继承、include）。想复用就复制粘贴，不做模板引擎。宁可笨，不要多一层求值。

### 7.3 `.fub` 的完整性模型：哈希能防篡改，不能防伪造

`.fub` 文件头里存着 32 字节符印，解码时**不采信**它，而是展开正文、重算 canonical、再比对。这样「改一个字节」与「改正文并重算符印」被区分开：

| 攻击 | 结果 |
| --- | --- |
| 改正文不动符印 | 拒绝（重算 ≠ 文件头） |
| 改正文并重算符印 | **通过（没有签名就挡不住）** —— 单测 `tampered_body_fails_the_seal_check` 与 `a_valid_body_with_a_stale_seal_is_rejected` 覆盖的都是第一行 |
| 追加垃圾字节 | 拒绝（严格模式不容忍尾部） |
| 换字典版本 | 拒绝（`fuwen_version` 不符即报错，不猜） |
| 换符名 | 拒绝（文件头符名与正文不符） |

**明确不承诺的事**：`.fub` 不证明作者身份。要防伪造得签名，而签名要密钥链（T27，未做）。现在能说的是「读出来的内容与写入时一致」，不能说「这张符是某人写的」。文档与 `fu info` 都按这个口径写，不越界。

### 7.4 复文：故意做小字典，把版本钉死

24 条片段、`0x01` 转义、最长优先匹配。收益只有十几个百分点，为什么还做：**符文正文里重复的是固定句式**（「只依据给定文本」「不要编造」这类安全约束），把它们换成一个字节，既省体积又让正文在二进制里更难被肉眼误改一点点——这是副产品，不是安全机制。

刻意不做的：通用压缩（zstd/gzip）。理由：解压要引依赖、要处理解压炸弹，而符文本就几 KB。字典带 `FUVEN_VERSION`，改字典必须升版本，旧文件宁可读不出也不许解错。

### 7.5 云篆：先把「版式」定死，再谈渲染

`yunzhuan.rs` 只输出 `CloudLayout`（纸面比例 3:5、符头/符胆/符脚各占千分比、行距 1.65 倍字高、每行 14 字、最多 18 行）与 6 种笔画基元的归一化折线。**一行绘制代码都没有。**

理由：排版规则若写在 UI 里，换皮肤就会变，云篆就不再是「编码」而是「装饰」。先由 `fulu-script` 定义版式，UI 只是把千分比乘上像素。T36 做渲染时不该再发明一套坐标。

### 7.6 入口唯一：`load_fu_file` 按内容识别

识别顺序：`FUB\x01` magic → 首个非空白字符是 `{` → 否则当中文 DSL。**不看扩展名**，因为扩展名会骗人（也会被用户改错）；实机验证里故意把三种形态分别命名成 `.txt` / `.bin` / `.dat`，仍全部识别正确。

CLI 的 `fu verify` / `fu seal` 本轮从「只读文本 + `inspect_fu`」改为走同一个门面：此前 `.fub` 传进去会被当成非 UTF-8 文本报错，导致「三种形态符印一致」这个结论没法用命令行自证。现在 `fu seal` 对三种形态输出同一串十六进制，且**符印一律重算**——若哪天有人图省事直接打印文件头那 32 字节，`seal_is_identical_across_all_three_forms` 会红。

GUI 同步改了：工作区扫描列 `.fu` / `.dsl` / `.fub` 三种；打开 `.fub` 时用 `load_fu_file` 读出后经 `dump_fu` 转成规范文本进编辑器，并明确提示「原文件不会被改写」。（界面交互本身未经真人验收，见 `docs/02` 第 27.5 节。）

### 7.7 残余风险

1. **无签名** → 只防篡改，不防伪造（7.3）。
2. **DSL 手写容易越界**：块内缩进必须两格、`#` 只能整行、不能嵌套。错误信息带行号，但用户仍会觉得啰嗦。
3. **复文收益依赖文案**：换一批非固定句式，折叠后可能只小几字节，`fu pack` 会如实报两种体积。
4. **`fu info` 的符印不可信**：它只读文件头、不解正文，输出里已标注「文件内记录，info 不校验」，校验必须用 `fu verify`。
5. **GUI 载入 `.fub` 未经真人点击**，只有单元测试与代码路径统一。

## 8. T42 iced 备选切换预案：什么情况下换、换哪些、换之前必须先做什么（2026-11-11）

所以把边界、清单、先后顺序先写死。

两条都保持「未测」——**未测不等于安全，只是还没撞上**。

### 8.2 隔离边界已经落在代码里，不是口号

`fulu-ui` 是唯一依赖 `eframe` 的 crate。这条以前只写在架构文档里，本轮把它变成测试
`crates/fulu-app/tests/ui_boundary.rs`：

- 逐个读 16 个 crate 的 `Cargo.toml`，断言 `fulu-core / register / provider / runtime / tools /
  app / audit / model / script / mcp / prompt / context / vault / orchestrator / skills / cli`
  里都没有 `eframe` / `egui` / `iced` / `winit` / `slint`；
- 同时断言 `fulu-ui` **仍然**依赖 `eframe` 且没有偷偷混入 `iced`——
  换栈必须走决策记录，不能靠一张清单悄悄完成。

只读清单不读源码：依赖边界是清单层的契约，比 grep 源码稳。

### 8.3 迁移面清单：三个文件重写、三个文件基本不动

| 现有文件 | iced 0.14 对应写法 | 工作量判断 |
| --- | --- | --- |
| `paper.rs`（版式 / 热区 / 命中测试，**纯数据**） | 原样保留 | **零改动**：不含任何 egui 类型，只有归一化坐标与权重 |
| `fonts.rs`（`include_bytes!` 思源黑体子集） | `iced::application(...).font(bytes)` / `Font::with_name` | 小改：换注入 API，字体文件与许可不变 |
| `confirm.rs`（`ChannelConfirmer`：mpsc + `ctx.request_repaint`） | 保留 channel，去掉 `Context`；由 `Subscription` 或 `Task::perform` 唤醒 | 小改：确认协议（敕可/敕否/三连 fail closed）不变 |
| `main.rs` 的 `logic`/`ui` 两段 | `Application` + `Message` 枚举 + `view` | **重写**：这是主要工作量 |
| `paper_view`（`egui::Painter` 自绘） | `iced::widget::canvas`（`Program` trait） | **重写绘制部分**，坐标换算与数据源不变 |
| 焚符线程 + `poll_burn` | `Task::perform` 或继续用手工线程 + `Subscription` | 中等：线程模型可保留，只是唤醒方式换掉 |

关键结论：**数据层（版式、热区、字段映射、笔画基元）与 UI 工具包无关**，这也是 8.2 那条测试
真正保护的东西。

### 8.4 迁移会失去什么（先说清，免得换完才发现）

- **即时模式的自绘便利**：egui 每帧重画，符纸「改一个字段立刻变」几乎零成本；iced 的 `canvas`
  需要自己管缓存与 `Message`，重绘粒度要重新设计。
- **`request_repaint` 这种「随手要一帧」**：iced 要用 `window::frames()` 订阅或 `Animation`，
  0.9 秒火光得换个写法。
- **~5 MB 的最小体积优势**（iced 默认带 wgpu 后端，体积与驱动依赖都更大；可以关到 `tiny-skia`
  软件渲染，但那是另一套取舍，需重新评估）。

### 8.5 换之前必须先做的事（顺序不能颠倒）

1. **T37 真人验收并留证据**（截图 / 录屏 + 一句话结论），否则连「为什么换」都说不清；
2. 用同一份验收清单记录 egui 的失分项，作为迁移后的对照基线；
3. 在 `crates/fulu-ui` 之外**不动任何 crate**的前提下，先只把 `main.rs` 的骨架换成 iced，
   跑通「打开、编辑、盖印、dry-run」四步；
4. 再补符纸 `canvas` 与敕门弹窗；
5. 全绿后删掉 eframe 依赖，`ui_boundary` 测试的「必须依赖 eframe」那条反向改掉——
   **这条断言存在的意义就是让换栈成为一次显式动作**。

### 8.6 本轮实际验证到什么程度

只做了「备选栈能不能在本机编出来并起窗口」这一件事，且是**独立空工程**里编的（不污染主工作区）：

- 工程：`D:/tmp/iced-spike`，只写一个 `text_input + button + text` 的最小 `Application`；
- 目的：确认 iced 0.14 在本机 Rust 1.99.1 / msvc 工具链上不需要额外系统依赖。

**结果（实测，非推测）**：

| 项 | 结果 |
| --- | --- |
| 依赖解析与编译 | ✅ 通过。`iced 0.14`（默认 features，含 `wgpu` 后端）共约 200 个 crate，`cargo build` 成功 |
| 窗口与事件循环 | ✅ 启动后连跑 4 秒未退出、无 panic（`timeout` 杀掉，退出码 124） |
| debug 二进制约 26.8 MB（未 strip，含 wgpu / winit） | 记下来给 8.4 的体积判断当参考，不做承诺 |
| **API 事实（易踩）** | iced 0.14 的入口是 `iced::application(boot_fn, update, view).title(..).run()`：**第一个参数是「怎么造初始 State」，不是标题**；标题走 `.title()`。这点与 egui 的 `run_native(title, options, creator)` 完全不同 |

**一个环境层面的坑（值得写下来）**：开了增量编译（默认）时，同样的工程在 `cryoglyph` 处
**16 分钟零 CPU**（rustc 进程还在、CPU 时间 0.03s），判为沙盒环境下增量缓存锁卡死；
加 `CARGO_INCREMENTAL=0` 后 23 秒编完。本项目 CI 不受影响（CI 无此沙盒），但本机若哪天
遇到「编译卡死不动」，先关增量编译再排查代码。

### 8.7 明确不做的事

- **不做「双栈并存」**：两套 GUI 依赖同在一张清单里，编译时间、体积、事件模型都会打架，
  且没人会同时维护两份界面。
- **不因为「egui 看起来不够像符」就迁移**：符箓台的观感问题（符纸比例、笔画、火光）
  在本轮 T36 里是用数据层 + 自绘解决的，与工具包无关。

## 9. T43 微调底本与云端供应商：产品决策（2026-11-11）

这一节回答两个「要不要做」的问题，都涉及钱、许可与数据出境，所以**只做决策，不写代码**。
两项的默认答案都是「不做」，并且把「什么条件下才做」写清。

### 9.1 微调：底本唯一，数据只从缴符链里来，产物必须可登记

**底本：`LiquidAI/LFM3-1.7B-Base`（BF16，3.46 GB），唯一。**

不用 Instruct 版当底本的三个理由：

1. **对齐数据不可追溯**：Instruct 版已经过别人的 SFT/DPO，再把自家数据叠上去，
   出问题时无法判断是「我们的数据」还是「别人的对齐」导致的；
2. **许可链更长**：底本越靠前，需要遵守的上游条款越少（仍受 LFM Open License v1.0 约束，
   商用营收 1000 万美元门槛不变）；
3. **可复现**：Base 权重是确定的起点，Instruct 的配方不公开，实验无法复现。

**数据从哪来（全部本地，默认不出门）**：

| 来源 | 内容 | 合规处理 |
| --- | --- | --- |
| 缴符链 JSONL | 每轮 `Invoked` / `ToolCall` / `ToolResult` / `Converged` 事件 | 复用 audit 的脱敏规则；密钥类字段本就从不入链 |
| 符文本（`.fu` / `.dsl`） | 系统提示词、目标、判据、工具白名单 | 用户显式导出才出目录；不含任何凭据（符内只有 `credential_ref`） |
| dry-run 差异 | 用户在「待焚」阶段改了哪里 | 只记字段名与次数，不记具体值 |

**必须遵守的三条**：

1. **不自动上传**：导出是显式命令（`fulu` 只写本地文件），训练在哪台机器跑由用户决定；
2. **脱敏先于导出**：与缴符同一套 redact 规则；含个人信息或密钥形态的样本直接丢；
3. **产物要登记**：训练出的 LoRA / 合并权重必须能转成 GGUF，并在 `models/manifest.json`
   新增槽位（如 `tuned`）固化 `bytes` 与 `sha256`——**没有摘要就不许当默认模型**。

**评测口径（拒绝通用 benchmark 自嗨）**：同一批 20 张符（覆盖只读/写入/召将/外宗四类），
比较三件事：① `success_criteria` 通过率；② 工具调用 JSON 合法率（非法参数即失败）；
③ 达成所需平均轮数。三者都不许比底本差，才谈「微调有效」。

**当前不做，原因写实**：本机无 GPU，训练要么在 CPU 上跑到不可接受，要么租云 GPU（持续花钱）。
这不是技术判断而是成本判断，需要用户明确批准预算后再启动；本轮只把口径定死。

### 9.2 云端供应商：默认关闭，且**当前不存在代码路径**

`Endpoint::parse` 只接受 `http://127.0.0.1` / `http://localhost`，这是有意的安全边界；
T13 的流式实现同样只在这条边界内。

六个准入条件（沿用 T13 设计稿，本轮更新状态）：

| 条件 | 状态 |
| --- | --- |
| 凭据只以 `credential_ref` 存在（T40） | ✅ 已实现（箓牒 + `lu://` 引用） |
| 默认路径本地回环；云端必须显式配置，缺失即报错 | ✅ 已实现（`Endpoint::parse`） |
| 远程端点走同一套「主机白名单 + 证书校验 + 禁重定向」 | ⚠️ 只有 MCP 侧（T19）有；**provider 侧未接** |
| 出网请求进缴符（只记主机与字节数，不记正文） | ❌ 未实现 |
| 流式/重试不产生重复计费 | ✅ 已实现（首个增量后即不可重试；`RetryPolicy::should_retry`） |
| 法务复核（数据出境 / 供应商条款） | ❌ 未做 |

**决策**：条件未齐之前，云端 provider **一行代码都不写**。理由不是「保守」，而是：
一个能被配置出来的出网路径，只要存在就会被人打开；而它的失败模式（数据出境、重复计费、
凭据泄漏）都是**不可撤销**的。

### 9.3 三条硬规矩（将来启用也必须遵守）

1. **不静默联网**：没有自动 fallback。本地不可用时明确报错并给出指引，
   绝不「悄悄改用云端」——这是从 M0 到现在的同一条规矩，不因功能增强而放宽。
2. **不做遥测**：不发使用统计、不发匿名性能数据。要改进就靠用户主动贴日志。
3. **供应商中立**：只对接 OpenAI 兼容协议，不绑定任何一家；切换供应商 = 改 `credential_ref`
   与一个 `model_id`，不写供应商专有分支。

### 9.4 若将来启用，最小可行切片的顺序

1. 出网事件进缴符（先有观测，再谈放行）；
2. provider 侧 TLS + 证书校验 + 禁重定向（可复用 T19 的口径与代码形状）；
3. `Endpoint` 增加「显式云端白名单」类型，与回环 `Endpoint` **不同类型**，
   免得「把云端地址塞进本地端点」这种混用；
4. 用户侧三道开关：配置文件、命令行显式参数、每次焚符确认卡片上写明「本符将出网」；
5. 法务复核 + `THIRD_PARTY_NOTICES.md` 补充供应商条款说明。

### 9.5 残余风险（明示）

- **微调数据可能过拟合符箓自己的句式**：24 条复文片段、固定安全句式会让模型「背题」，
  评测集必须包含没见过的目标类型，否则通过率是假的。
- **LoRA 合并后许可仍需复核**：底本 LFM Open License v1.0 的商用门槛同样约束微调产物，
  不是「自己训的就能随便卖」。
- **云端一旦启用，缴符链里会出现主机名**：这本身是可审计的好处，但也意味着一份「曾访问过
  哪些服务商」的记录留在本地，需要写入 `SECURITY.md` 的隐私说明。
