## 2. T13 云端 provider / SSE 流式 / 能力协商（设计稿，未实现）

### 2.1 现状与边界

`fulu-provider` 目前只有 `LocalLfmProvider`：`std::net::TcpStream` 手写 HTTP/1.1，端点被 `Endpoint::parse` 限制在 `127.0.0.1` / `localhost` 明文回环，无流式、无重试、无证书概念。这是**有意为之的安全边界**，不是欠账。

T13 的目标是「先把扩展面设计清楚，再决定实现」，因此本轮**只定接口与语义，不改实现、不改边界**。

### 2.2 能力协商字段

```rust
pub struct Capabilities {
    pub streaming: bool,            // 已有：服务端是否支持增量返回
    pub tool_calls: bool,           // 已有
    pub local_only: bool,           // 已有：数据不出本机
    pub max_context_tokens: u32,    // 已有
    // 新增提案
    pub parallel_tool_calls: bool,  // 一次回复里多个 tool_calls 是否可并行执行
    pub json_schema_mode: bool,     // 结构化输出是否支持 json_schema（而非 json_object）
    pub vision: bool,               // 是否接受图像内容块（与 T18 上游配套）
    pub reasoning_blocks: bool,     // 是否返回独立 reasoning 文本（需在提示词层过滤）
    pub max_tools_per_request: u16, // 0 = 不限；用于箓层裁剪工具表
}
```

**兼容规则**：新增字段必须有 `Default`，旧实现通过 `..Default::default()` 保持编译；未知能力一律取**保守值**（`false` / `0`），绝不默认「支持」。

### 2.3 流式抽象

```rust
pub enum StreamEvent {
    TextDelta(String),
    ToolCallDelta { index: u16, id: Option<String>, name: Option<String>, arguments_chunk: String },
    Usage(Usage),
    Done { finish_reason: String },
}

pub trait Provider: Send + Sync {
    fn id(&self) -> &str;
    fn capabilities(&self) -> Capabilities;
    fn invoke(&self, req: &InvocationRequest) -> Result<InvocationReply, ProviderError>;

    /// 默认不支持流式：老实现无需改动。
    fn invoke_stream(
        &self,
        _req: &InvocationRequest,
        _sink: &mut dyn FnMut(StreamEvent) -> StreamControl,
    ) -> Result<InvocationReply, ProviderError> {
        Err(ProviderError::NotImplemented("streaming"))
    }
}

pub enum StreamControl { Continue, Cancel }
```

**关键语义（不可妥协）**：

1. **流式不改变仪轨**：`invoke_stream` 的返回值仍是完整 `InvocationReply`，工具调用必须**全部收齐后**统一过箓核验与敕门，绝不边流边执行。
2. **半途失败即整轮失败**：流断在中间不拼出「半个回执」；已收到的文本只进缴符事件（标注 `partial`），不回喂模型当成功。
3. **取消即释放**：`Cancel` 之后必须关闭连接并停止计费统计，`usage` 标 `estimated`。
4. **确定性**：同一请求两次流式调用的「事件序列最终归并结果」必须等价于非流式结果，用快照测试锁定。

### 2.4 SSE 解析口径

- 只认 `data:` 行；`event:` 仅用于区分 `ping` / `error`，不改变解析主路径。
- `[DONE]` 结束；空行是事件分隔，不是结束。
- `tool_calls` 按 `index` 归并增量（`id`/`name` 只在首个增量出现，`arguments` 逐段拼接），拼接结果必须能被 `serde_json` 解析，否则判 `Protocol` 错误而非猜测。
- 单事件上限 1 MiB、整轮上限 8 MiB（与 `MAX_RESPONSE_BYTES` 同源），超限直接断流。
- 服务端不返回 `usage` 时标 `estimated=true`，不伪称精确。

### 2.5 超时与重试（统一策略）

```rust
pub struct RetryPolicy {
    pub max_attempts: u8,        // 默认 3
    pub base_backoff_ms: u64,    // 默认 400，指数退避 + ±20% 抖动
    pub retry_on: RetrySet,      // Timeout / Transport / HttpStatus(429,500..=599)
}
```

- **只在没有产生任何可见副作用时重试**：非流式可重试；流式一旦发出首个 `TextDelta` 就**不可重试**（避免重复计费与重复输出）。
- 429 优先采信 `Retry-After`，缺失才用退避表。
- 每次重试必须落缴符事件（`retry` 计数），不静默重试。
- 重试总时长受符的 `timeout_secs` 硬约束，超出即 `Timeout`（过坛）。

### 2.6 云端 provider 的准入条件（未满足前不实现）

| 条件 | 状态 |
|---|---|
| 凭据只以 `credential_ref` 存在（T40），符内零明文 | 未实现 |
| 远程端点必须走 T19 的同一套「主机白名单 + 证书校验 + 禁重定向」政策 | T19 已落地（MCP 侧），provider 侧未接 |
| 默认路径仍是本地回环；云端必须是显式配置项，缺失即报错 | 已由 `Endpoint::parse` 保持 |
| 出网请求进缴符（只记主机与字节数，不记正文） | 未实现 |
| 法务复核（数据出境 / 供应商条款） | 未做 |

**结论**：T13 本轮交付「设计 + 接口草案」，实现排在 T40（凭据库）之后；在那之前云端 provider 不存在任何代码路径。

## 3. T19 远程 MCP（HTTPS 边界）威胁模型与实现口径

### 3.1 为什么这是「安全边界变更」

原先的不变量只有一条：**fulu 只与回环地址说明文 HTTP**。它一次性消掉了整类风险——没有 TLS 就没有证书校验问题，没有公网就没有 SSRF、没有凭据外泄、没有中间人。放开远程 MCP 等于把这条不变量拆成一组需要逐条守住的新不变量。

### 3.2 资产与威胁

| 资产 | 威胁 | 缓解 |
|---|---|---|
| 用户 API token | 被写进符 / 配置 / 缴符 / 日志；被重定向到攻击者主机 | 只允许 `${ENV:VAR}` 引用；启动时解析、只在内存；缴符与日志统一脱敏；禁重定向 |
| 本地网络 | SSRF：借 MCP 访问内网 / 元数据服务 | 远程端点必须 `https://` 且主机命中 fulu 自有白名单；白名单**不接受 IP 字面量**与 `localhost` |
| 传输内容 | MITM / 降级 / 伪造证书 | 系统信任库校验（不提供 `--insecure` 开关）；`--proto =https` 禁降级；非 TLS 端口握手失败即报错 |
| 响应体 | 超大响应拖爆内存；恶意块 | 8 MiB 硬上限、60s 超时、64 KiB 正文截断、非文本块显式告警 |
| 审计链 | 密钥进事件 | `Authorization` / `Cookie` / `X-Api-Key` 等头部在落盘前脱敏，只记「N 个请求头」 |
| 模型 | 服务端内容提示注入 | 外宗输出一律是不可信文本；工具调用仍过箓 + 敕门，远程内容不能提升权限 |

### 3.3 实现口径（本轮落地）

1. **不引入 TLS 依赖**：HTTPS 交给系统 `curl`（Windows 走 Schannel/系统证书库，Linux/macOS 走系统 CA）。理由是 T14 moli 已验证同一条思路——把「首个 TLS 依赖例外」用「复用用户既有工具」消解，fulu 自身依赖树保持零 TLS。
2. **白名单文件**：`~/.fulu/remote-mcp.json`（fulu 自有，不碰任何 MCP 生态配置）：
   ```json
   { "allow_hosts": ["mcp.example.com", "*.trusted.dev"] }
   ```
   支持 `*.` 前缀通配（只匹配一级以上子域，不匹配裸域）；IP 字面量与 `localhost` 一律拒绝。
3. **凭据引用**：MCP 配置里的头部值可写 `${ENV:VAR}`；含敏感头部（`authorization` / `cookie` / `x-api-key` / `api-key`）却写成字面量的，**直接拒绝连接**并提示改用环境变量。
4. **传输硬约束**：`--proto =https`、`--max-redirs 0`、`--tlsv1.2` 起、`--max-time` 60s、`--max-filesize` 8 MiB。
5. **失败如实**：curl 退出码 + 首行 stderr 回传（不含头部值），绝不伪装成功。

### 3.4 残余风险（明示，不掩盖）

- 恶意 server 仍可返回带指令的文本——缓解是「它仍只是一条工具结果」，不获得任何额外权限。
- token 对 server 天然可见（协议要求）；只能保证它不出现在 fulu 的磁盘与日志里。
- 系统 `curl` 缺失或版本过旧时远程链路不可用：属于**如实降级**，不影响本地 stdio / 回环 HTTP。

## 4. T16 摄行电脑控制：权限与风险评估（写码前置）

### 4.1 能力定义（拟）

| 工具 | 动作 | 平台 |
|---|---|---|
| `shexing.type` | 向当前前台窗口输入文本 | Windows（SendKeys） |
| `shexing.key` | 发送组合键（如 `^s`、`{ENTER}`） | Windows |
| `shexing.click` | 移动光标并点击（左/右） | Windows |
| `shexing.screenshot` | 截屏写入工作区文件 | Windows |

### 4.2 风险判定

摄行是**全系统唯一能以「用户本人」身份操作任意窗口**的能力：它不受工作区路径约束，也不受命令行白名单约束。一次误操作可能删文件、发消息、点「确认」按钮。

因此分级为：

- **权限**：`Limited`（与其它内置工具同级，不新开权限档），但**默认不注册**——不开启时工具在名册里根本不存在，模型连看到的机会都没有；
- **风险**：`Destructive` + `EveryCall`（每一次调用都必须人点头，**不允许**用 `--allow-risk destructive` 批量预授权，也不允许「每符一次」）；
- **双重解锁**：环境变量 `FULU_ALLOW_SHEXING=1`（进程级）+ CLI `--shexing`（会话级）。任一缺失即不注册，理由是「最高权限要两把钥匙」；
- **参数全量展示**：确认页必须显示将输入的**完整文本**、坐标、目标文件路径，不允许「略」。

### 4.3 审计与限额

- 每次调用（含被拒）落缴符事件：动作类型、参数字节数、结果、耗时；截屏事件不落图片内容，只落路径与字节数。
- 配额：每符 20 次（防止模型陷入无限点击循环）。
- 截屏只能写入工作区（复用 `resolve_workspace_path`），不联网、不进提示词（除非用户显式把文件喂回去）。

### 4.4 残余风险与结论

- 无法阻止「用户点了确认但没看清参数」——只能靠确认页把参数展示到最完整；
- 无法阻止目标窗口本身是恶意程序；摄行不引入新漏洞，只是把用户已有的风险转成可审计的操作；
- **结论**：按 M4 交付，默认关闭、逐次确认、Windows 优先；跨平台（macOS Accessibility / Linux xdotool）单独立项，不在 v0.3 范围。

## 6. T40 箓牒（凭据库）：方案取舍与残余风险（2026-11-11）

### 6.1 要解决的问题

在 T40 之前，`credential_ref` 只是一个**受箓白名单里的字符串**：`fulu-register` 会核验「这条引用有没有受箓」，但**没有任何代码真正去取密钥**。于是有两个未闭合的缺口：

1. 云端 provider 一旦接上（T13），密钥从哪来；
2. 「符内绝不写密钥」这条红线，只靠成符阶段的字面量扫描（`looks_like_secret`）把关，**运行期无凭据可依**。

T40 补齐的正是这一段：新增 `fulu-vault`（代号「箓牒」），把「引用 → 密钥」的解析做成受控、可审计、可失败的一步。

### 6.2 两条路线，选了「委托系统工具」

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 链接原生 SDK（`keyring` crate / Win32 `CredRead` / libsecret） | 能力强，但 Windows 要 `windows-sys` + `unsafe`，Linux 要 dbus / 静态链接 libsecret，三平台各一套 | **否** |
| 委托系统自带工具（本方案） | 要求目标机器有对应工具；缺失时如实报错并指路 | **采纳** |

理由与 moli 复用系统浏览器、T19 复用系统 `curl` 做 TLS 校验是同一条：**不把平台 SDK 拖进依赖树**，也不让 `unsafe` 蔓延。代价是「工具不在就不可用」，而这恰好可以被**文件后端**兜住。

### 6.3 后端矩阵

| 平台 | 工具 | 取 | 存 | 删 | 密钥是否进 argv |
| --- | --- | --- | --- | --- | --- |
| Windows | `powershell.exe` + WinRT `PasswordVault` | 脚本常量、引用名经环境变量 | **stdin** | 脚本常量 | 否 |
| macOS | `security` | `find-generic-password -w` | `add-generic-password -U -w <密钥>` | `delete-generic-password` | **是（已登记为残余风险）** |
| Linux | `secret-tool` | `lookup` | `store`（**stdin**） | `clear` | 否 |

Windows 侧脚本是**常量字符串**，用户提供的引用名只经 `FULU_VAULT_USER` 环境变量传入，因此不存在引号/换行注入面；有测试锁住「脚本里不出现 ref、不出现格式化占位符」。密钥一律不进环境变量（同用户可读 `/proc/self/environ`）。

### 6.4 文件后端：为什么新增密码学依赖

系统凭据库在 headless Linux、CI、受限 Windows 上都可能不可用，需要一个可搬运的兜底。**手写密码学是错的**，因此引入 RustCrypto：

- `chacha20poly1305` 0.10（AEAD，MIT OR Apache-2.0）
- `pbkdf2` 0.12 + 既有 `sha2`（KDF，MIT OR Apache-2.0）
- `zeroize` 1（密钥清零，MIT OR Apache-2.0）

边界声明：**只用于「系统凭据库不可用」时的加密落盘，不参与任何网络握手**；TLS 依旧零依赖（远程 MCP 走系统 `curl`）。`cargo deny` 与 `cargo audit` 均覆盖这三个 crate，本机实测四项全绿。

参数：PBKDF2-HMAC-SHA256 **600000** 次、16 字节随机盐、ChaCha20-Poly1305 12 字节随机 nonce、**AAD 绑定引用名**（把 `cloud.cred` 改名成别的名字也解不开）。

落盘格式（UTF-8 文本，便于人眼确认「这里面确实没有明文」）：

```text
fulu-vault-v1
ref lu://default/cloud
kdf pbkdf2-sha256:600000
salt <32 hex>
nonce <24 hex>
ct <hex 密文 + 16 字节 tag>
```

另有两条防护：读取时把 `kdf` 行声明的迭代次数**夹到 `[1000, 10_000_000]`**（畸形文件不能把进程算死）；写盘先写 `.tmp` 再改名（中途失败不留半个密文），Unix 下目录 `0700`、文件 `0600`。

### 6.5 语义：箓牒里有这条引用 = 已受箓

`fulu-register` 的 `grant_credential` 此前没有任何调用者，`lu://default/local` 之外一切引用都会被驳回。T40 定下的规则：

> **`AltarSession::use_vault()` 把箓牒里登记的引用逐条写进名册**，因此「库里有」等价于「已受箓」。

这样不需要再引入一份新的授权配置文件，也不会出现「授权与凭据两处不一致」。反过来，`vault rm` 之后引用不再受箓，引用它的符会被驳回（CLI 输出里明说这一点）。

### 6.6 闸门顺序：破符 → 凭据 → 授箓 → 其余

`AltarSession::dry_run` 现在先做 `fu.validate()`，再做凭据解析，最后才进法坛的 `prepare`（其中含授箓核验）。理由：

- 结构都不对的符，谈凭据与授权没有意义；
- 凭据问题比笼统的「未受箓」更好定位——在 6.5 的规则下，补救动作就是 `fulu vault put <引用>`，错误信息直接给出该命令。

`ignite` 侧的红线：**没 `confirmed` 就一个字都不碰凭据库**。有计数测试锁住「dry-run 取 1 次、未确认时仍是 1 次、确认后恰好 2 次」。

### 6.7 已知残余风险（不遮掩）

1. **macOS 的 `security add-generic-password` 只能从 argv 收密钥**，同用户下 `ps` 可见。缓解：文档明示、优先建议在 macOS 上用 Keychain Access 手工存入，或改用文件后端。这是本方案唯一一处「密钥短暂出现在进程参数里」。
2. **Linux `secret-tool` 依赖 D-Bus 会话**，headless / 容器里会失败。失败时如实报 `BackendUnavailable` 并提示改用 `FULU_VAULT_PASSPHRASE`，**不会**偷偷写到明文文件。
3. **`FULU_VAULT_PASSPHRASE` 是环境变量**，同用户可见。这是「非交互场景必须给出一个入口」与「不落明文」之间的妥协；交互式输入尚未实现，登记为后续项。
4. **系统凭据库无法枚举**（三平台都没有可移植接口），`list` 读的是只含引用名的 `~/.fulu/vault-index.json`；索引在 ≠ 密钥可取，`get` 仍可能 `NotFound`。文件后端则直接枚举磁盘目录，比索引可信。
5. **Windows `PasswordVault` 在无用户会话的服务上下文可能不可用**，此时报 `BackendUnavailable`。

### 6.8 本轮实机验证（Windows，`x86_64-pc-windows-msvc`）

| 场景 | 结果 |
| --- | --- |
| 文件后端 `put` → 落盘 → `get` | 通过；`.cred` 文件里 `grep` 不到密钥与口令（0 命中） |
| 口令错 | `无法解密：口令不对，或文件被改过（AEAD 校验失败）`，退出码 1 |
| 把密文换到别的引用名下 | 拒绝（AAD 绑定生效，单测覆盖） |
| 系统凭据库 `put` → `get --reveal` | 通过，取回值与写入完全一致（跨进程，非内存残留） |
| 系统库条目的位置证明 | 换一个 `FULU_HOME` 仍能取到 → 密钥确实在 OS 库，不在路径下 |
| 明文零落盘 | `FULU_HOME` 下只有 `vault-index.json`（仅引用名），全目录 `grep` 密钥 0 命中 |
| `vault rm` 后 | 取不回（退出码 1），`list` 为空；测试条目已清理 |
| 云端符无凭据 `altar dry-run` | 拒绝并给出 `fulu vault put` 指引，退出码 1 |
| 已存凭据 `altar dry-run` | 通过，确认页写明「已从箓牒取出（焚化时作为 Bearer 注入）」 |

未做：macOS `security` 与 Linux `secret-tool` 两条分支**未在真机执行**（本机只有 Windows），只验证了命令构造与解析（单测断言密钥不进 argv、退出码映射、脚本常量性）。这一条如实登记，不写成「三平台已验」。
