## 0. 四条规矩

1. **一条一行判定**，只填 `通过` / `不通过` / `部分` / `不适用`。不写「应该没问题」「大致正常」。
2. **先记录，再改代码**。现象、按键序列、期望与实际都要留；先改代码会让「这是回归还是老问题」永远说不清。
3. **证据是截图**，存 `docs/acceptance/<日期>-<平台>/`。涉及 IME 的截图里必须同时有：窗口、输入框里的预编辑串、输入法候选框。
4. **结论只写一次**，在第 7 节。`TODO.md` 的勾选以第 7 节为准，不以「测试全绿」为准。

> 特别提醒：`cargo test` 全绿、CI 三平台编译通过、窗口能起来 5 秒——这三件事**都不等于** T37 / T38 通过。
> eframe 没有稳定的 headless 测试通道，GUI 的手感只能人看。

### 3.3 事件日志怎么用（定位用，不是判定依据）

底部探针会打印 `Event::Ime(...)` 的 `Debug` 形式，回答「事件到底有没有来」：

- 正常一次输入应看到：`Preedit { text: "fu", ... }`（可能多次，逐字母变化）→ `Commit("符箓")`。
- 只有 `Commit` 没有 `Preedit`：预编辑串没交给 egui（可能由输入法自己画），要结合截图判断候选框与内联串的实际表现。
- `Preedit { text: "", active_range_chars: ... }`：egui 0.37 的 Windows legacy 预编辑视觉与「新视觉」差异，记录并截图。
- 一条都没有：输入法根本没连上窗口，先查系统输入法是否对当前窗口生效。

**日志只能证明「事件到了」，证明不了「人看着对」**——判定必须以眼睛为准。

### 3.4 不通过时先做的三件事

1. 换输入法复测：Windows 微软拼音 / 搜狗；Linux fcitx5 / ibus 各一次（Linux 是 IME 最容易挂的平台）。
2. 换缩放复测：100% 与 150% 各一次（候选框定位在缩放非 100% 时最容易错位）。
3. 换编辑器复测：探针单行框与正文多行框分别记——egui 里这两条路径实现不同，可能只有一个坏。

三条都复现，才算「egui 路线不达标」。

## 6. 缺陷记录格式

每个「不通过 / 部分」都要有一条，编号写进用例表的「观察」列：

```markdown
### D-01 ｜ IME-08 ｜ 严重度：阻断 / 严重 / 一般

- 复现：启动 → 载入示例符 → 正文第 3 行行首输入「符箓」（微软拼音 24H2）
- 期望：预编辑串出现在光标前
- 实际：预编辑串出现在行尾；上屏后光标跳回行首（截图 03-ime08.png）
- 频率：3 / 3 次
- 复测：换搜狗同样复现 / 换搜狗不复现
- 初步定位（可选，不是结论）：
```

严重度口径：
- **阻断**：P0 用例失败（T37 直接判不通过）。
- **严重**：P1 失败且影响正常使用（如敕门卡片无法点击、保存丢内容）。
- **一般**：P1 / P2 失败但可绕过。
